## Purpose

提供可追溯的未导入数据识别与解释能力，按已确认的 SUP 专用过滤策略分析文件记录，区分不支持的配置与正常业务丢弃，保存记录标识、过滤规则和业务原因，并允许通过配置标记可忽略记录。

## ADDED Requirements

### Requirement: 未导入结论采用 SUP 专用规则
系统 MUST 按本规范的 SUP 策略处理本文件启用过滤规则，不枚举普通流程或还原普通实例上下文。支持规则按 `ruleid` 顺序执行，保留 `whereexplain` 的适用条件语义，表达式中的 `insttype` 为 SUP 实例类型；适用规则按 AND 组合，第一条正常执行但不通过的规则生成丢弃结论。所有适用规则通过或没有规则时不生成丢弃记录；不支持的配置导致文件任务失败。

#### Scenario: 直接通过规则后还有拒绝规则
- **WHEN** 一条记录依次经过直接通过的 `5` 规则和不满足条件的 `X` 规则
- **THEN** 记录仍被 `X` 判定为丢弃，前一条规则通过不使整个文件规则链直接结束

#### Scenario: 支持规则不适用
- **WHEN** 一条支持的规则的 `whereexplain` 在 SUP 上下文中不成立
- **THEN** 跳过该规则并继续后续规则，不借用普通 NODE 的实例类型重新求值

### Requirement: 不支持方式报告完整配置位置
系统 MUST 在读取本文件启用规则时拒绝方式 `1/6/4`，使文件任务失败，并返回 `intfid:${intfid},fileid:${fileid}过滤规则ruleid:${ruleid}不支持全量转入`；占位值必须替换为实际接口标识、文件标识及配置中的完整原始规则编号。不得把该错误转换成可忽略的丢弃记录，也不得用过滤方式编码代替规则编号。

#### Scenario: 任一不支持方式被启用
- **WHEN** 文件启用规则中包含方式 `1`、`6` 或 `4`
- **THEN** 报告指定格式的错误并使文件任务失败，不将该文件标记为分析或持久化完成

#### Scenario: 空文件或适用条件不匹配
- **WHEN** 启用规则包含不支持方式，但文件为空、该规则适用条件不匹配或前一规则会提前结束逐记录判断
- **THEN** 仍在规则配置校验中报告该不支持规则，不能静默跳过错误

### Requirement: 指定账户相关方式直接通过
系统 MUST 对方式 `2/3/5/7/P` 的 SUP 过滤判断直接返回通过，不再根据账户存在性、指定状态、托管单元、证券或基金管理人匹配结果拒绝记录，也不执行原过滤分支专属的必填因子校验。文件解析、字段转换及适用条件表达式自身的错误处理保持原有职责。

#### Scenario: 原过滤匹配条件均不满足
- **WHEN** 适用规则为 `2/3/5/7/P` 中任一方式，原过滤所查询的账户或基金信息不存在，或指定状态、托管单元、证券不匹配
- **THEN** 当前 SUP 规则仍通过，不因该方式生成丢弃记录，并继续后续规则

### Requirement: 席位查询后的 SUP 判断采用三个条件
系统 MUST 在方式 `X/T` 查询 `comm_seatconfig` 后，仅在席位存在、`domainid` 与本次 SUP 上下文匹配且 `outflag != '1'` 时通过，否则不通过。该查询后分支不得再附加分区或主分区限制，也不得被账户存在标志、共享席位开关或 `importUnExitsSeat` 反转。查询前的现有逻辑和特殊分支保持，包括 `X` 的报价回购处理、跨市场席位替换及既有市场补充。

#### Scenario: 席位满足三个条件但分区不匹配
- **WHEN** 席位存在、业务域匹配、`outflag != '1'`，但席位分区不包含 SUP 当前分区
- **THEN** 查询后分支返回通过，不再检查 `partids/mainflag`

#### Scenario: 任一必要条件不满足
- **WHEN** 席位不存在、业务域不匹配或 `outflag='1'` 中任一情况成立
- **THEN** 查询后分支返回不通过，账户存在、允许共享席位或导入未配置席位的标志不能改变该结果

#### Scenario: 保留查询前特例
- **WHEN** `X` 规则命中现有查询前报价回购处理或跨市场席位替换条件
- **THEN** 保持该特例原有行为；若后续进入席位查询，则使用 SUP 三条件判断

#### Scenario: 普通 NODE 席位开关不跳过 SUP 规则
- **WHEN** 参数 `67014` 允许普通 NODE 跳过 `X/T`，当前执行实例为 SUP
- **THEN** 不借用普通 NODE 身份跳过规则，仍按 SUP 规则适用条件及席位逻辑处理

### Requirement: 证券与记录字段过滤保持原逻辑
系统 MUST 对 SUP 方式 `S/R` 保持现有行为：`S` 的证券代码为空时通过，非空时在指定市场列表中匹配 `comm_stock`，不增加证券模板兜底；`R` 支持字段集合包含或排除，多个条件按 AND 组合，字段值及集合项去首尾空格、区分大小写并完整值匹配。

#### Scenario: 证券代码为空或只命中模板
- **WHEN** `S` 规则的证券代码为空，或证券代码非空且仅命中证券模板而未匹配 `comm_stock`
- **THEN** 前者通过，后者不通过，保持既有证券过滤行为

#### Scenario: 字段包含与排除组合
- **WHEN** `R` 规则同时配置字段包含和排除条件
- **THEN** 仅全部条件满足时通过，任一条件不满足时拒绝，大小写及空格处理与原逻辑一致

### Requirement: 丢弃记录关联到原始记录
系统 MUST 保存 `sup_filedropdata`，以 `intfid+fileid+id+busidate` 唯一标识文件丢弃记录，并保存丢弃规则编号、`dropruledesc` 业务原因描述、丢弃忽略标志；`id` 必须直接取解析后对象中类型为 `int/bigint` 的同名属性值，与该文件全量记录保持一致，不因线程、批次或重做而重新编号，日期或文件不同的记录不得串联。

#### Scenario: 使用解析后的整数记录编号
- **WHEN** 解析后对象包含类型为 `int` 或 `bigint` 的 `id` 属性，且该记录被判定为未导入
- **THEN** 丢弃记录保存相同的 `id` 数值，并按接口、文件和业务日期关联该源记录，`bigint` 数值不截断为较小整数类型

#### Scenario: 当天不同文件具有相同记录序号
- **WHEN** 当天两个文件出现相同的记录序号
- **THEN** 各记录仅关联到自身接口、文件及当天业务日期的丢弃原因，不要求保留过去日期的数据

#### Scenario: 重做得到相同结果
- **WHEN** 相同文件和业务日期在源数据及规则不变时重做
- **THEN** 丢弃记录不重复，关联到相同源记录，原因和忽略标志一致

#### Scenario: 多线程处理不改变记录编号
- **WHEN** 多线程或不同批次处理同一组具有有效 `id` 的解析对象
- **THEN** 丢弃记录仍使用各对象原有 `id`，不以线程局部序号或处理完成顺序替代

### Requirement: 丢弃原因确定且可解释
系统 MUST 为丢弃记录保存明确的业务过滤原因；多个规则可导致丢弃时，按确定的规则顺序选取首个决定性原因。`dropruleid` MUST 直接保存该命中规则的原始 `comm_filefilterrules.ruleid`，字段与原始编号保持同域同类型，不得改存 `filtermethod`、另行编码或截断；`dropruledesc` MUST 描述同一规则的拒绝原因。其他上下文可以记录在流程日志中，不得通过重复主键记录保存多个原因。过滤分析必须区分业务拒绝与执行异常。

#### Scenario: 规则编号与过滤方式不同
- **WHEN** 记录被 `ruleid='A'`、`filtermethod='X'` 的规则拒绝
- **THEN** 丢弃记录的 `dropruleid` 保存原始编号 `A`，不保存方式编码 `X`，原因描述对应规则 `A`

#### Scenario: 同一过滤方式配置多个规则
- **WHEN** 同一文件存在方式相同但原始编号不同的规则，不同记录分别被其中某条规则首次拒绝
- **THEN** 各丢弃记录保存各自命中规则的原始编号，可结合接口及文件定位具体规则，不合并为过滤方式编码

#### Scenario: 同一记录触发多个拒绝规则
- **WHEN** 同一记录存在多个可说明丢弃的规则
- **THEN** 丢弃表中仅有一条记录，重复分析选取相同的决定性原因

### Requirement: 丢弃描述说明实际拒绝原因
系统 MUST 在 `dropruledesc` 中保存本条记录在命中规则中实际触发的具体拒绝原因，不直接复制配置中的规则描述，不仅返回“过滤不通过”等笼统文字。描述 MUST 与 `dropruleid` 对应同一决定性规则，并遵守字段长度约束；超长上下文留日志，字段内保留核心原因。补充原因输出不得改变已确认的过滤条件、短路顺序或 `S/R` 原有判断结果。

#### Scenario: 席位规则不同拒绝分支
- **WHEN** `X/T` 规则分别因席位不存在、业务域不匹配或外部共享席位拒绝记录
- **THEN** 分别保存对应的具体原因，即使规则编号相同也能区分实际拒绝分支

#### Scenario: 证券规则拒绝
- **WHEN** `S` 规则因指定市场未匹配证券而拒绝记录
- **THEN** 描述说明“指定市场未找到证券”，不以规则名称代替拒绝原因

#### Scenario: 字段条件规则拒绝
- **WHEN** `R` 规则因某字段不在允许集合中或命中排除集合而拒绝记录
- **THEN** 描述指出该字段及其未满足的包含或排除条件，保持原过滤判断结果

### Requirement: 忽略规则按接口和文件精确匹配
系统 MUST 通过 `sup_filedropignorerule` 保存规则编号、接口标识、文件标识及条件表达式；仅对已判定未导入的记录评估同一 `intfid+fileid` 下全部适用忽略规则，满足任意一条则将 `dropignoreflag` 置为 `1`，否则置为 `0`。表达式必须支持方案中的 `xwh in ('1','2') and zjzh = '123'` 形式。

#### Scenario: 任意一条忽略规则命中
- **WHEN** 一条丢弃记录匹配该接口及文件下多条规则中的一条
- **THEN** 丢弃记录保留，忽略标志为 `1`，原始记录和丢弃原因仍可查询

#### Scenario: 没有匹配忽略规则
- **WHEN** 没有配置规则或所有适用规则均未命中
- **THEN** 忽略标志为 `0`，其他接口或文件的规则不得影响该记录

#### Scenario: 忽略规则非法
- **WHEN** 规则表达式语法错误或引用了不存在的字段
- **THEN** 系统明确报告配置错误并使本次文件分析失败，不得静默标为忽略或成功完成

### Requirement: 忽略规则直接读取 COMM 磁盘表
系统 MUST 在 Cache 阶段仅当 `m_bSupFileImport` 为 true 时调用独立的 `InitSupIgnoreRules()`，该函数封装本次局部规则清空、参数读取、文件字段校验、忽略配置读取与预解析及连接恢复。每次全量导入通过 `CSup_filedropignorerulePhydbManager` 直接从 COMM 磁盘库按接口、文件读取忽略规则，并恢复原连接上下文。该表不使用 MemDB，不配置内存加载，不依赖该表的 CacheManager；逐记录求值复用本次读取结果。磁盘读取失败必须使本次文件任务失败，不能退回上次快照或按无规则继续。

#### Scenario: 内存库没有忽略规则表
- **WHEN** MemDB 未创建或未加载 `sup_filedropignorerule`，COMM 磁盘库存在相应规则
- **THEN** 仍能通过 PhydbManager 读取并执行这些规则，忽略标志按 COMM 磁盘规则生成

#### Scenario: 同一次导入处理多条源记录
- **WHEN** 当前接口和文件的规则已从 COMM 读取并完成预解析
- **THEN** 各解析线程复用本次只读规则，不逐记录查库；下次全量导入重新读取规则

#### Scenario: 磁盘查询或规则预解析失败
- **WHEN** COMM 规则查询失败或本次规则预解析报错
- **THEN** 恢复调用前的数据库连接上下文并向现有文件任务失败处理传播异常，不继续生成成功结果

### Requirement: 每次全量导入清空文件旧结果并重新生成
系统 MUST 在每次 SUP 内存文件全量导入的 `Before()` 中，按当前 `intfid+fileid+busidate` 三条件同时相等删除 `sup_filedropdata` 旧内存结果，业务日期使用当前清算业务日期；其他接口、文件或业务日期的记录 MUST 保留。旧结果删除 MUST 在解析前实际完成，删除失败终止本次导入。前处理通过 MemdbManager 条件删除并检查返回值，条件字段必须为 intfid。后续各读取调用独立收集本次结果并随源批次写入，不使用共享 CacheManager、前缀或 resultMutex，`Write()` 不重复写回。系统 MUST 重新执行过滤分析和本次重新加载的忽略规则，生成丢弃记录及忽略标志；非 SUP、导出及直接导入磁盘不得触发该前处理清理。磁盘持久化沿用当前三条件范围；运行未完成或失败时不得将旧结果作为本次成功结果查询。仅重试持久化沿用本次生成数据，不等同于再次执行全量导入分析。

#### Scenario: 忽略规则修改后再次全量导入
- **WHEN** 上次已生成丢弃记录，忽略规则修改或删除后再次运行该文件全量导入
- **THEN** 在 Before 删除当前接口、文件和业务日期的旧结果，使用本次忽略规则重新生成记录及 `dropignoreflag`，原忽略标志不被继承

#### Scenario: 本次已无丢弃记录
- **WHEN** 上次存在丢弃记录，本次文件为空或全部记录通过过滤
- **THEN** Before 已删除当前 `intfid+fileid+busidate` 的旧结果，本次完成后同范围丢弃结果为空，不残留上次记录

#### Scenario: 前处理清理范围隔离
- **WHEN** 当前 SUP 内存导入开始，表中同时存在当前三条件记录、同名文件但不同接口记录、其他文件及其他业务日期记录
- **THEN** 仅当前 intfid、fileid、busidate 同时匹配的记录在 Before 删除，其他记录保留；该删除不等待 Write

#### Scenario: 非 SUP 或非内存导入
- **WHEN** 当前任务为普通实例导入、SUP 导出或 SUP 直接导入磁盘
- **THEN** Before 不删除 sup_filedropdata，不触发 SUP 分析缓存处理

#### Scenario: 前处理删除失败
- **WHEN** Before 删除旧内存结果发生异常
- **THEN** 本次导入失败，不继续 Cache 规则加载或文件解析，不写入本次成功结果

#### Scenario: 同主键再次生成
- **WHEN** 本次重新生成与已删除旧结果相同联合主键的丢弃记录
- **THEN** 新结果进入本次读取调用的局部批次并纯插入写回，不重复提交旧删除，不因保留旧结果而主键冲突；本次生成数据自身重复键必须报错，不能改为更新

#### Scenario: 仅查询而未重新运行
- **WHEN** 修改忽略规则后仅查询已经持久化的分析结果，未重新运行全量导入
- **THEN** 查询返回已持久化的忽略标志，不在查询时重新执行忽略规则

### Requirement: 忽略不改变未导入事实
系统 MUST 将“未导入”和“允许忽略”作为两个独立属性；允许忽略不得使记录被物理删除、隐藏丢弃原因或被宣称已导入常规业务流程。

#### Scenario: 查询全部未导入数据
- **WHEN** 用户选择只查看未导入数据
- **THEN** 结果包含允许忽略及未被忽略的丢弃记录，并展示忽略标志供用户区分

### Requirement: SUP 席位业务域使用确定值
系统 MUST 对当前 `GetDomainid()` 使用相等匹配，不解释为所有业务域；`01` 仅是实例初始化样例。

#### Scenario: 席位属于其他业务域
- **WHEN** SUP 实例业务域为 `01`，查到的席位业务域为 `02`
- **THEN** 当前席位规则不通过，丢弃原因记录业务域不匹配，即使该席位非外部共享也不能通过

#### Scenario: 席位属于业务域 01
- **WHEN** SUP 当前 GetDomainid() 为 `01`，查询到业务域 `01` 的席位且 outflag 不为 `1`
- **THEN** 席位三条件匹配通过，仍继续评估后续规则

### Requirement: 席位业务域取当前运行参数
系统 MUST 将 X/T 席位业务域与当前 `GetDomainid()` 相等比较，不把初始化样例 `01` 写入判断。

#### Scenario: 当前业务域不同于初始化样例
- **WHEN** 当前 SUP 的 GetDomainid() 为 02，席位存在且非外部共享
- **THEN** 席位域为 02 时通过该查询分支，席位域为 01 时按业务域不匹配拒绝


### Requirement: SUP 过滤统一复用父类内存查询方式
`CFilterManagerSup` MUST 沿用父类 `CFilterManager` 的 MemdbManager 访问内存表，不使用 CacheManager 或 CacheManagerPtr。X/T MUST 复用父类已初始化的席位管理器和 GetMainseat/GetTradeseat 查询及聚合语义，再执行席位存在、当前业务域匹配、outflag 非外部共享三个条件。Cache 阶段不再预加载过滤专用席位缓存。丢弃结果采用读取调用独立的 MemdbManager 批次，COMM 磁盘忽略规则仍使用 PhydbManager。

#### Scenario: 查询托管席位和交易席位
- **WHEN** SUP 的 X 或 T 规则进入席位查询
- **THEN** 分别使用父类 MemdbManager 的 GetMainseat 或 GetTradeseat，不依赖 Cache 阶段席位缓存；市场补充、查询前特例、三条件及具体拒绝原因保持

#### Scenario: 同一席位对应多条配置
- **WHEN** 同一市场及席位存在多条配置，其中包含外部共享标志
- **THEN** 直接沿用父类查询函数的聚合结果，SUP 按聚合后的业务域与 outflag 判断，不额外构造缓存聚合策略


### Requirement: 丢弃记录按读取调用独立批量写入
系统 MUST 为每次 SUP ReadFileData 调用创建独立 CSup_filedropdataMemdbManager，并显式传给逐条解析处理；本地容器不在线程之间共享，不从共享工厂或跨任务 static thread_local 取得。满批及尾批 MUST 在源批次成功写入后提交对应非空丢弃批次，使用 WriteLocalVecToMemdb(false) 纯插入及底层表级锁，成功后清批；不得仅在文件结束时积累全部结果。结果上下文只保留只读规则，不使用 resultMutex 或结果 CacheManager。

#### Scenario: 多线程及线程复用
- **WHEN** 多个读取调用并行处理分段，或同一线程随后处理其他文件
- **THEN** 每次调用独立持有并释放管理器与批次，不带入旧文件数据或旧功能号指针；仅批量入库时由表级锁保护

#### Scenario: 满批尾批及空批
- **WHEN** 源数据达到原批次阈值或读取结束，丢弃批次为非空或空
- **THEN** 源批次成功后写入非空丢弃批次并清空，尾批独立检查自身条数；空批不写库、不因返回 0 报失败，Write 阶段不重复写入

#### Scenario: 源或丢弃批次失败
- **WHEN** 源批次写入失败，或源写入成功后丢弃批次写入失败
- **THEN** 前者不提交对应丢弃批次，后者不宣告文件成功；异常传播到任务，禁止后续持久化，未提交容器随调用退出销毁且析构不写库。两表不保证原子回滚，重跑前按当前三条件删除旧丢弃结果

#### Scenario: 同一导入生成重复主键
- **WHEN** 本次批次内或跨线程生成相同联合主键的丢弃记录
- **THEN** 纯插入按底层失败机制报错，不使用默认插入或更新覆盖另一条分析记录

#### Scenario: 普通实例读取
- **WHEN** 普通实例调用 ReadFileData
- **THEN** 默认不创建附加结果管理器，保持原过滤及源数据写入行为
