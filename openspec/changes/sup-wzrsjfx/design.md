## Goals / Non-Goals

**目标：**

- 以文件与业务日期为分析单位，形成源记录、丢弃原因、忽略标志、持久化状态的完整关联。
- 按已确认的 SUP 专用过滤策略识别分析记录：不支持方式报错、账户类指定方式直接通过、席位类调整判断、证券和字段类沿用原逻辑。
- 新增 SUP 功能采用单一功能号模式，复用七阶段框架；文件级动态任务承担并行粒度。
- 普通导入、历史查询与未传新参数的接口调用保持兼容。

**非目标：**

- 不新增“已导入但未生成清算流水”的识别算法，不接入日间清算。
- SUP 库仅保存当天数据，本期不提供历史数据保留、历史查询或历史归档能力。“当天”按当前清算业务日期判断，不按服务器自然日期猜测。
- 不重构整个文件导入框架，不切换到 `cbs_file/io_convert` 新入口。
- 不把格式损坏、数据库异常解释成正常业务过滤；不自动决定生产客户启用清单或删除保留策略。

## Decisions

### 1. 数据模型与存储职责

保留方案中的表和字段定义，字符业务标志在实现中使用已有或新增业务宏。

| 对象 | 变更及含义 |
| --- | --- |
| `comm_if_file.supflag` | 全量导入标志，字符标志，默认 `0-否`，`1-是` |
| `comm_if_file_log.persiststatus` | 本次文件日志的持久化完成标志，默认 `0-否`，全部写入成功后 `1-是` |
| `sup_filedropdata` | `comm` 模型分组；字段见下表，运行结果落 SUP |
| `sup_filedropignorerule` | COMM 磁盘配置表；直接通过 `CSup_filedropignorerulePhydbManager` 读取，不访问 MemDB |
| `comm_instance` | 配置 `insttype=9` 的 SUP 实例与连接信息，凭据沿用部署管理方式 |

`sup_filedropdata`：

| 字段 | 类型 | 约束/业务含义 |
| --- | --- | --- |
| `intfid` | `VARCHAR(32)` | 联合主键，接口标识 |
| `fileid` | `VARCHAR(64)` | 联合主键，文件标识；以模型 `KDT_FILEID` 为准 |
| `id` | `BIGINT` | 联合主键，文件记录序号，逐条关联源记录 |
| `busidate` | `INTEGER` | 联合主键，业务日期 |
| `dropruleid` | 与 `comm_filefilterrules.ruleid` 同域同类型，当前为 `CHAR(1)` | 直接保存命中的决定性过滤规则的原始 `ruleid`，不保存过滤方式编码 |
| `dropruledesc` | `VARCHAR(128)` | 本条记录被命中规则拒绝的具体原因，如“席位不存在”，不直接复制配置中的规则描述 |
| `dropignoreflag` | `CHAR(1)` | `0-未被忽略`、`1-忽略` |

`sup_filedropignorerule`：按用户确认以当前模型为准，`id BIGINT` 为主键，`intfid VARCHAR(32)`、`fileid VARCHAR(64)`、`rulecontent VARCHAR(128)`，按接口与文件取全部规则并进行任一命中判断。

模型分组不等于部署库路由：配置/流程/日志仍由相应 COMM 数据源管理，丢弃运行结果及全量接口数据必须能在同一 SUP 连接完成关联查询。SUP 初始化仅初始化所需 `comm` 分组中的 `sup_filedropdata`；全量接口表按启用文件元数据动态建立。忽略规则表仅在 COMM 磁盘库初始化，执行时直接通过 `PhydbManager` 读取，不配置 MemDB 加载、不使用该表的 `MemdbManager/CacheManager`，也不依赖其内存表存在。读取结果可在本次功能局部保存供逐记录求值。

理由：保留独立分析数据能查询被过滤的原始记录；仅保存丢弃计数无法解释单条数据。日常持久化状态表已有其他状态语义，不复用其字符值冒充新的二值 `persiststatus`。

### 2. 单功能号与模块落点

| 功能 | 实现决策 |
| --- | --- |
| `supFlowPrepare` | 在`macbs-service仓库`中新增java的`modules/supfile`模块，并加入到`macbs-service`和`macbs-node`两个bootapp的依赖中。在其中新增bex接口，继承`ClearBase`类，作为流程任务负责节点映射及动态任务 |
| `660030` | `cbs_memdb_sync` 内新增 SUP 单功能号加载入口，局部复用加载通用逻辑 |
| `625092` | 保留原注册，工厂遇到 SUP 导入时创建 `CKfIntfProcessToMemSup` |
| `supFilePersist` | java的`modules/supfile`模块中新增bex接口，继承`ClearBase`类，作为流程任务,负责调用c++框架的前处理和持久化逻辑 |
| `supFlowCleanup` | Java BEX 直接删除本流程引用的持久化配置组及 SUP 节点映射，不调用 C++ 清理内存库 |

方案未要求恢复/分片/执行三个对外功能号，因此选择单功能号；持久化内部复用前处理不是对外三段式。新入口同时维护所属模块 `CMakeLists.txt`、实际 `export.cpp`、`frame.xml` 和流程配置。避免在公共框架增加 SUP 专属分支。

七阶段职责：`GetBusiParam` 解析日期、接口、文件和流程上下文；`Before` 初始化，SUP 内存导入在此按当前 `intfid+fileid+busidate` 删除旧丢弃结果；`Cache` 加载配置和依赖；`Check` 校验节点、规则、文件映射；`Clear` 生成任务或计算分析结果；`After` 汇总；`Write` 提交结果及成功标志。异常由 `Fault` 及框架日志处理，返回值只前进或结束。

新增内存表业务访问默认使用 `CacheManager`，全生命周期只读表优先 `CacheManagerPtr`。按用户明确确认，`CFilterManagerSup` 的内存表查询统一沿用父类 `CFilterManager` 的 `MemdbManager` 方式，不使用 `CacheManager/CacheManagerPtr`，不增加过滤专用缓存预加载。丢弃结果按用户确认改为每次 `ReadFileData()` 调用持有独立的 `CSup_filedropdataMemdbManager`，不使用共享 CacheManager 或逐条结果互斥锁；忽略规则仍通过 `PhydbManager` 读取 COMM 磁盘配置。批量缓存设置容量边界。现有加载/持久化基础设施可通过封装后的既有入口复用；必须明确其实际写入阶段，不宣称通用加载器在 `Write` 才落库。

### 3. 动态任务图与资源管理

流程 `9` 无前置流程，四个步骤按方案编号配置；步骤 20、30保留占位任务并按现有调度约定处理空任务。用户已确认本期不考虑席位、证券等基础数据是否已就绪，不增加就绪检查、等待机制或前置流程，也不将外部就绪保证列为实施及验收前置条件。

准备任务按本次流程执行上下文读取 `supflag=1` 清单，先校验后分配空闲节点。节点选择沿用现有占用检查，不新增共享表锁或流程行锁；映射及任务变更在同一 COMM 事务提交，保存 `comm_inst_compute_node_map`；无空闲节点明确失败，不抢占普通清算节点。

1. 在步骤 10 **只生成一个**`660030` 数据加载任务，参数为 `cfg_group=sup`，前置任务为当前的`supFlowPrepare`任务，创建匹配 SUP 实例和节点的 `comm_flowrecordresult`。

该任务面向整个非空文件清单，共享加载本次过滤依赖；透传实际 SUP 实例及业务域、分区参数，不绑定单个 `intfid/fileid`。空文件清单不生成加载任务。

对每个 `intfid+fileid`：

1. 在步骤 20 生成 `625092`，参数 `intfid=${intfid}|fileid=${fileid}|`，`exectype='1'`，`beforerecordno` 指向上述唯一加载任务，创建任务结果。
2. 在步骤 30 生成 `supFilePersist`，使用相同文件参数，`exectype='0'`，`beforerecordno` 指向该文件导入任务；任务结果按该执行类型的引擎约定产生。

任务级依赖由 `beforerecordno` 维护；**跨步骤依赖能绕过步骤自身激活条件**。动态任务使用 `PRE_RECORD`，初始任务及结果均为 `runflag=0`，由前置完成驱动可执行。

准备重做按业务日期、流程运行上下文、接口、文件定位已有任务和映射；如果流程计算节点映射表中已经存在当前流程的分配计算节点，则不需要重新分配。但是**必须**删除动态生成的所有任务并重新生成。只复用/清理本次范围，唯一键与提交边界避免重复任务。步骤 40 仅在所有文件持久化成功后释放节点及临时对象，不删除 SUP 磁盘数据或完成状态；失败保留可恢复上下文，由明确的失败恢复操作清理。

实施落点：流程模板采用现有管理节点流程类型，模板任务均在管理节点执行。`supFlowPrepare` 在同一 COMM 事务内完成节点选择、映射和任务结果插入，不新增共享表锁或流程行锁。运行时先按 `insttype=9` 识别当前流程已有映射并复用；无映射时，延续按任务当前业务域选择 SUP 实例的方式，不校验样例编号、名称、分区或节点数。映射、任务参数及任务结果使用实际实例值。

每次准备删除本流程预留编号段内的加载、导入、持久化任务及对应结果，同时删除旧任务引用的临时持久化配置，再根据当前启用清单重新生成；加载任务清理仍覆盖原 `100100～190099` 编号段，兼容删除旧版逐文件加载任务。模板准备、占位和清理任务定义保留；步骤 20/30/40 及后续占位、清理模板结果重置为等待本次执行，防止旧成功状态使新流程提前完成。原日志和磁盘结果保留。唯一加载任务编号固定为 `100100`，文件导入、持久化任务编号分别从 `200100/300100` 递增；非空清单共生成 `1+2×文件数` 个动态任务及对应结果。新结果编号重新申请，`import_result_id` 引用本次新导入结果。全部操作在同一事务，生成异常回滚。空启用清单同样删除旧动态任务，不新增加载、导入或持久化任务；已有节点留待成功清理释放，无映射时不新增节点。

准备任务成功回调立即刷新引擎任务图，并清除当前流程的完成和已驱动缓存；不能等待包含新加载任务的步骤完成才刷新，也不能继承旧任务编号的完成状态。原有其他动态任务与普通流程的分配行为保持。

成功清理由 Java `supFlowCleanup` **不需要**调用 C++功能清理内存数据库。**需要**直接在java中删除本流程任务参数引用的持久化配置组及本流程 SUP 节点映射。任一步失败均不执行后续正常释放。

保留全部文件持久化完成检查，包含尚未激活任务及任务结果，并核对任务业务日期；未完成或失败不执行正常释放。Java 在 COMM 数据源调用 `SupFlowService.release`，先删除当前流程任务引用的临时持久化配置，再按 `insttype=9` 识别并删除本流程 SUP 映射，两类删除处于同一事务，任一步异常回滚。空清单或重复清理没有待删记录时可正常结束；其他流程配置及映射、内存数据、磁盘分析结果、任务结果及日志保留。移除本变更新增的 `660031/CleanupSupMemdb` 专用实现、导出及 Linux/Windows 注册，不再以计算节点远端调用成功作为清理前置。

### 4. 全局依赖加载与判定口径

新增加载入口接收 `cfg_group=sup`，映射到通用组件使用的 `cfggroup` 语义，使用精确配置组匹配。对 `source_inst_type='1'` 遍历全部当前`domainid`的类型 `1` 实例，对其他源实例类型按现有配置路由，目标始终为本次 SUP 分析上下文。加载的表根据配置决定，**不是**指定的七张表：`comm_accountmapped`、`node_publicfundcustinfo`、`comm_seatconfig`、`comm_stk_template`、`comm_stock`、`node_rptselfrunsecuid`、`intf_sfhg_secuinfo`。

如果需要对于`comm_accountmapped`表加载，直接复用通用加载中的按照`settgroup`取模加载方式，但是**必须**调整加载sql为只读取`market,secuid,fundacct,settunit`四个字段, 以减少网络IO。

结合手工代码调整，账户映射实际加载只接受全表配置，由 SUP 内部适配为四字段完整取模 SQL，再复用通用分段；不要求外部配置 :instance_node SQL，外部 SQL 加载方式明确报错。空表方式仅清空目标表。

其他表复用现有的通用加载方式；

实施复用模块内 CMemdbSyncShared 的参数替换、取模/条数/结算分组分段和流读取能力。类型 1 路由在 SUP 局部适配，通用入口默认路由保持。账户投影使用 SUP 局部读取器，避免通用 GetLoadSQL 自动恢复全字段；未读取模型字段使用默认值，直接沿用通用写入行为，不另行回查或比较主键及字段内容。Cache 缓存配置及当前业务域实例，Clear 只清空本次启用配置中的目标表，再启动通用异步加载流水线，Write 沿用基类阶段；不再保留原七表全量快照后统一写入的实现。加载失败阻断导入，重做重新替换本次配置表。

SUP 加载器继承 CAsyncMemdbSync，直接复用 AsyncLoad、m_PrepareQueue、m_ProcessQueue、准备线程、读取调度线程及 CJstpThreadPool、独立写入线程。准备回调仅提交分段；读取完成仅提交管理器到写入队列；不得在准备回调中同步完成读写。Clear 只启动一次流水线，等待三条线程链路完成后返回，Write 保持基类阶段。

通用加载仅提供分段生成、读取管理器创建和单批读取三个可派发扩展点，默认实现保持普通加载逻辑。读取表管理器扩展点命名为 `CreateLoadTableManager()`，同步通用声明、实现、读取线程调用及 SUP 重写和清表调用，避免成员名遮蔽全局工厂 `CreateLoadManager()`；跨版本检查继续通过原全局工厂获得 `ILoadManager*`。SUP 分段遍历当前业务域源实例，队列使用模块内 CMemdbLoadTask 携带配置副本及源实例名称，不修改模型或 DAO。每个读取任务建立独立来源适配器；已排队任务不读取准备线程可变的当前源实例。账户四字段投影及完整余数覆盖保持。

SUP 与通用线程驱动使用同一份加载参数，threadnum 控制读取线程池，并复用 prepare_queue_size、process_queue_size、timeout、队列背压、完成通知、活动任务超时诊断、异常汇总和退出等待。SUP 在线程启动前拒绝非正队列容量和超时。空表方式仅清表，空配置不启动流水线。准备、读取或写入失败按通用机制结束并向功能号报告，未完成全部写入不得报告共享加载成功；不新增取消已提交任务的策略。

文件过滤配置沿用现有读取方式；

忽略规则不属于上述内存加载清单，每次文件导入在 Cache 阶段通过 `CSup_filedropignorerulePhydbManager` 独立读取 COMM 磁盘表。

多实例合并**不需要**考虑主键冲突问题。移除 SUP 专用主键去重、字段内容比较及冲突报错，读取批次经 m_ProcessQueue 交给通用 WriteDataToMemdb，沿用现有批量插入及失败后插入或更新策略；底层读取、写入异常仍使加载任务失败并阻断导入。

### 5. 导入子类、原因与忽略表达式

`CKfIntfProcessToMemSup` 负责“评估后始终保留记录”，`CFilterManagerSup` 负责“返回过滤结论及业务原因”。现有过滤器为值成员且相关方法未必为虚函数，实施需将最小范围的创建/过滤/过滤后处理点改为可派发接口，确保子类实际执行，不能仅声明同名方法造成静态调用旧实现。

SUP 过滤方式逐项约定如下；普通实例沿用现有实现。

| 过滤方式 | SUP 处理 |
| --- | --- |
| `1` 资金账号、`6` 客户代码、`4` 市场＋股东＋交易单元 | 不支持全量转入，报错：`intfid:${intfid},fileid:${fileid}过滤规则ruleid:${ruleid}不支持全量转入` |
| `2` 市场＋股东＋指定状态、`3` 市场＋股东＋托管单元、`5` 市场＋股东、`7` 市场＋股东＋托管单元＋证券、`P` 基金管理人客户信息 | 该过滤方式直接返回通过，不再调用原账户、指定状态、托管单元、证券或基金管理人匹配逻辑；其中 `7` 的证券检查也一并跳过 |
| `X` 托管席位、`T` 交易席位 | 基于现有逻辑调整查询 `comm_seatconfig` 之后的判断：席位存在，且 `domainid` 与本次 SUP 上下文匹配，且 `outflag != '1'` 时通过，否则不通过 |
| `S` 市场＋证券、`R` 导入记录字段值集合 | 保留现有逻辑不动 |

不支持方式在读取本文件启用规则时统一校验，保留配置中的原始 `ruleid` 用于报错；不能因空文件、前一规则短路、`whereexplain` 不匹配或因子缺失而绕过该错误。错误模板中的值替换为实际接口、文件和规则编号，不用 `filtermethod` 或另行映射的编码代替配置 `ruleid`。

对支持方式，规则适用条件 `whereexplain` 沿用现有语义，`insttype` 为 SUP 本身的值；`2/3/5/7/P` 的“通过”只作用于当前规则，不跳过后续 `X/T/S/R`。这些直接通过的方式不再要求原过滤分支的账户类入参校验或表查询；独立的文件解析、字段转换和规则适用表达式错误仍正常报告。

`X/T` 席位查询复用父类 `m_pComm_seatconfigMemdbManager` 及 `GetMainseat/GetTradeseat` 的 MemdbManager 重载，沿用父类席位聚合行为，不自行构造 CacheManager 查询结果。`X/T` 保留查询前的入参解析、市场补充，以及现有查询前特殊分支；`X` 的报价回购业务处理和 `SH_QTSL` 跨市场席位替换因此仍适用。进入席位查询后，判断统一为上述三个条件，取消该段的 `partids/mainflag` 限制，不再因“账户已存在”、共享席位开关或 `importUnExitsSeat` 改成其他结论。外部共享席位 `outflag='1'` 在此查询分支不通过。参数 `67014` 原本只对普通 NODE 跳过规则，SUP 不借用普通 NODE 身份绕过 `X/T`。实现中使用业务宏表达标志含义。

`S` 保留证券代码为空直接通过、非空时在给定市场列表中查询 `comm_stock` 的逻辑，不增加证券模板兜底；`R` 保留集合包含/排除、多个字段条件 AND、去首尾空格、大小写敏感和完整值匹配逻辑。

SUP 路径取消当前“实例 9 直接通过”的短路；预过滤只做必要解析优化，不跳过待保存记录。正式过滤与插入主键过滤也需逐个核对，确保重复业务主键的不同源记录仍有独立记录身份。源 `id` 按文件记录稳定确定，多线程不能用线程局部序号造成冲突；每条记录的id直接用解析完成后的对象中的`id`属性值，取值方式通过`CMemdbTableEnhancer`实现.如果对象中没有`id`属性或者`id`不是`int/bigint`类型，则允许报错

每条源记录先按 SUP 专用规则得到通过或丢弃结论；只有支持规则正常执行且不通过才产生 `sup_filedropdata`。多个拒绝原因采用确定顺序的首个决定性规则，完整上下文写日志。不支持方式引发文件任务失败，不写成可忽略的业务丢弃原因。`dropruleid` 直接保存命中的首个决定性规则在 `comm_filefilterrules` 中的原始 `ruleid`，与该字段保持同域同类型；不使用 `filtermethod`、自定义编码映射或截断值。同一过滤方式下不同规则保留各自编号，并结合 `intfid/fileid` 定位配置。`dropruledesc` 描述本条记录在同一命中规则中实际触发的具体拒绝原因，不直接复制配置中的规则描述，也不能仅写“过滤不通过”。

原因在实际拒绝分支生成：`X/T` 席位查询后分别描述“席位不存在”“业务域不匹配”“外部共享席位”；`S` 描述“指定市场未找到证券”；`R` 指出具体不满足条件的字段及包含/排除条件，例如“字段 xwh 不在允许集合中”或“字段 xwh 命中排除集合”。保留的其他拒绝分支也应说明实际原因，描述与 `dropruleid` 对应同一决定性规则。只补充原因输出，不改变已确认的过滤条件、短路顺序及 `S/R` 原有判断结果。字段内保留可理解的具体原因，遵守 `VARCHAR(128)` 长度约束，超长上下文写日志，不能因细节过长丢失核心原因。

`Cache()` 仅在 `m_bSupFileImport` 为 true 时调用独立函数 `InitSupIgnoreRules()`。该函数负责清空本次局部规则、读取接口和文件参数、切换及恢复连接、校验文件字段、查询忽略配置与预解析表达式；移除 `Cache()` 中 SUP 过滤使用的席位缓存预加载，过滤时直接使用父类已初始化的 `m_pComm_seatconfigMemdbManager`。忽略规则初始化函数切换到 COMM 磁盘连接，通过 `CSup_filedropignorerulePhydbManager` 按本次接口、文件读取，随后恢复原连接上下文；在 `Cache/Check` 阶段预解析并校验字段，使用现有表达式求值能力的适用部分，对源字段求值，支持 `in`、等值和 `and` 组合。读取不经过 MemDB，不在每条源记录求值时重复查库。非法表达式或未知字段使文件任务失败，不执行原始 SQL，不静默忽略。多个规则任一命中即置忽略标志，但不删丢弃记录。

上述 `PhydbManager.CacheAll()` 执行 COMM 磁盘查询并保存到管理器局部容器，不等同于 MemDB 加载。每次运行先清空功能局部规则，再重新读取和预解析；查询或预解析异常恢复原连接并向现有任务失败处理传播，不回退到旧规则。此流程仅用于 SUP 内存导入，既有导出及直接导入磁盘路径不加载忽略规则。

每次运行 SUP 内存文件全量导入（包括此前已成功后的再次运行）都在 `CFileManage::Before()` 按当前 `intfid+fileid+busidate` 删除 `sup_filedropdata` 的旧结果，再重新执行过滤分析和忽略规则，生成新的丢弃记录及 `dropignoreflag`；不沿用上次丢弃记录或忽略标志，也不只更新仍然存在的记录。三个清理条件必须同时相等，业务日期取 `GetBusidate()`；其他接口、文件或业务日期的记录保留。忽略规则每次运行重新加载，配置变更在下次全量导入重新生成时生效，查询只读取本次持久化结果。空文件或本次无丢弃记录时，该文件旧结果同样清空。

按用户确认的前处理时点落实替换：`Before()` 先确认 SUP 内存导入并使旧持久化成功状态失效，再通过 `SupFileImportBefore()` 中的 `CSup_filedropdataMemdbManager` 按 `intfid+fileid+busidate` 执行条件删除。修正错误字段名 `initfid` 为 `intfid`，检查 `Delete()` 返回值，失败抛异常且不进入规则加载与解析。非 SUP、导出或直接导入磁盘不执行该清理。

丢弃结果改为读取调用内独立批量写入：`ReadFileData()` 通过 `CreateFilterResultManager()` 创建局部 `unique_ptr`，SUP 返回新的 `CSup_filedropdataMemdbManager`，普通导入返回空指针。管理器显式传入 `ReadOneRecord()` 和 `FilterParsedRecord()`，不存入共享成员或工厂，不使用跨任务保留的 `static thread_local`。每条丢弃记录完成原因和忽略标志计算后只加入本次管理器的本地容器，移除 `CSup_filedropdataCacheManager`、前缀与 `resultMutex`；`CSupFileContext` 只保留只读规则快照。

满批源数据仍在 `ReadOneRecord()` 写入，尾批仍在 `ReadFileData()` 写入；两处均在源数据成功后调用 `WriteFilterResultBatch()`。按丢弃管理器自身条数判断空批，空批直接返回，不把返回 0 视为失败。非空批使用 `WriteLocalVecToMemdb(false)` 纯插入，复用管理器内部表级写锁和条数核对；成功后清空本地容器，重复主键不得通过更新掩盖。批次容量随现有源数据批次限制，尾批不依赖源 count 是否为零而遗漏刷新。读取调用正常或异常结束时由局部所有权销毁管理器，析构不执行写库，线程复用不带入旧记录。`CFileManage::Write()` 不再写回丢弃缓存。

源数据和丢弃结果分两次写入，不承诺跨表原子性；源写入失败不提交对应丢弃批次，丢弃写入失败使读取线程及文件任务失败，后续持久化不得执行，旧成功状态保持失效。部分已写内存数据由重新导入时的源表准备和同三条件丢弃清理替换。磁盘持久化保持当前 `intfid+fileid+busidate` 范围；仅重试持久化使用本次已生成数据，重新运行全量导入才重新读取和执行忽略规则。

理由：用子类隔离可减少普通导入回归面；直接修改所有实例过滤结果或只记录计数无法满足记录级解释。

### 6. 单文件持久化与重试

SUP 仅存储当前清算业务日期的全量记录和丢弃结果；本期不建立按日期的历史表，也不为历史查询给原接口表增加日期字段或历史主键。`sup_filedropdata.busidate` 仍用于记录本次分析日期，文件日志及流程状态必须匹配当天。当天数据准备、失败重做和同日文件隔离仍需保证一致性。

`supFilePersist` 根据文件配置确定目标表，建立 `cfg_group=sup_${fileid}` 的配置，包含源数据表和该文件的丢弃记录范围。表名来自服务端文件元数据，不接受自由拼接。当前仅启用 `SHJS/SH_JSMX01`，持久化分组为 `sup_SH_JSMX01`，源表为 SUP 库的 `sh_jsmx`；本期不要求提取多文件共表的批次条件，也不将同名文件跨接口碰撞处理列为当前交付前置条件。不要求原接口表包含 `intfid/fileid/busidate` 字段。丢弃记录仍按当前接口、文件及业务日期限定范围。

新增持久化配置时，Java 使用当前任务参数中的 instid，通过 COMM 数据源查询 comm_instance，取 instname 作为源表及丢弃表配置的 dbname。不得写死为 sup，也不直接信任任务中传入的 instname。实例不存在或 instname 为空时在替换配置前失败；查询及两条配置替换在同一事务内完成。

`supFilePersist`接口本身为java实现。在其中再通过`KcpsClient`调用C++的持久化前处理和持久化功能号。

Java 调用时沿用系统现有请求组装方式，将任务上的参数透传给对应 C++ 功能号；SUP 的实例、节点、配置组、文件范围及动态建表参数由任务配置和现有参数约定承载。调用结果、异常、超时及重做处理维持系统当前行为，不新增 Java 侧远端运行状态轮询、C++ 停止确认或超时后的重试准入判断。

持久化前处理在启用 dynamic_create_table 时，只对本次已筛选配置中 globaldeletesql 为空、纯空白或去除前导空白后以 truncate 开头的表执行动态重建，前缀大小写不敏感；delete 开头及其他非空前缀均跳过动态建表，继续原有删除和持久化流程。

允许重建的表依据对应 MemdbManager 的字段及主键定义，直接执行 DROP TABLE IF EXISTS 后 CREATE TABLE，不查询是否存在，也不使用 CREATE TABLE IF NOT EXISTS 保留旧结构，使后续版本模型变化可以在重跑时生效。删除或建表失败均使前处理失败，不继续调用 600001。未启用参数时沿用原行为。源表的 truncate 配置会重建，sup_filedropdata 的 delete 配置保留现有表及其他文件数据，由部署脚本维护其结构。

在本次 SUP 实例、节点和文件范围执行持久化前处理及写入；不能调用默认“全部清空/全部持久化”参数。`sup_filedropdata` 沿用当前持久化配置，按本次 `intfid+fileid+busidate` 删除旧结果并写入本次重新生成的结果。开始全量导入或重做使文件旧成功标志失效，依据现有调用返回结果确认全量和丢弃写入成功后，最后更新本次导入日志的 `persiststatus=1`，不另建远端状态判定机制。

SUP 数据与 COMM 日志可能无法处于同一事务：不要求跨库分布式事务，使用“数据提交在先、完成标志在后”的可恢复顺序。标志更新失败按失败处理，通过系统现有重做机制再次执行时，按同范围幂等替换并补写标志；本期不扩展超时与并发重试控制。禁止因部分表成功而向查询开放半份数据。合法空文件也清理同范围旧结果并正常完成。

### 7. 查询接口与页面

`commIfIntfQueryAll` 的 `supflag` 为可选字符参数。未传时严格保留原先启用状态、`ZDQL_` 排除、分组和排序逻辑；传 `1` 增加全量文件筛选，删除空分组。同步修改参数对象、BEX 映射和 DAO 查询。

原方案查询请求/响应未填写，本设计补充以下业务契约，封装格式沿用项目统一分页返回约定：

| 请求字段 | 约定 |
| --- | --- |
| `busidate` | 必填，必须等于当前清算业务日期；不支持历史或未来日期 |
| `intfid`、`fileid` | 必填，选择的已授权全量文件 |
| `tableName` | 页面通用组件需要时传入，服务端验证其与文件配置一致；实际表名由配置解析 |
| `onlyNotImported` | 可选布尔值，默认否；是时只返回丢弃记录 |
| `pageNo`、`pageSize` | 分页；正整数并采用项目既有上限 |
| 动态字段条件、排序 | 复用既有页面的已校验字段契约，字段和排序方向受文件元数据约束 |

分页响应使用现有 `PageListResult` 提供源记录列表、总数及分页信息；字段元数据由页面复用现有 `getColumnNameList` 接口获取。记录追加 `id`、`busidate`、`notImported`、`dropruleid`、`dropruledesc`、`dropignoreflag`。通过过滤的行原因与忽略属性为空，不能把空值解释为被丢弃。

`querySupDiskDBByTableName` 服务端先核验请求日期等于当前清算业务日期、文件权限、当天流程完成状态和对应持久化标志，再切换到 SUP 只读数据源。当前按 `SHJS/SH_JSMX01` 配置解析 `sh_jsmx`，读取该文件当天的全量记录，不增加针对 `SH_JSMX02/03` 的批次筛选适配。使用源对象 `id` 与丢弃表关联，并在丢弃表一侧限定请求的 `intfid/fileid/busidate`；不假设源表存在这三个字段。全量查询左关联，只查未导入时使用等价的内关联/存在性过滤。分页总数与列表共用筛选条件并按稳定记录键排序。条件值使用参数绑定，动态表/列由白名单解析；请求结束恢复原数据源上下文。

使用当前流程信息和文件导入日志核验当前业务日期的成功状态，不新增历史流程状态查询链路。请求非当天日期直接提示“SUP仅支持查询当前业务日期数据”；当前流程状态缺失、日期不符、执行中或失败时拒绝查询，不能用前一日完成状态放行。

页面沿用“历史接口及登记公司数据查询”的文件树和动态列布局，业务日期限定为当前清算业务日期，去掉“查询历史数据”，增加“只查看未导入数据”，显示原因与忽略标志。实际落点为 `macbs-web/public/lcp-common/common_qry/pages/QueryStatistics/SupFileAnalysis/Index.json` 和专用 `SUP_FILE_ANALYSIS.json` 模板，菜单编号 `606049900`，页面路由 `/renderer/index?code=common_qry-QueryStatistics-SupFileAnalysis`。文件树传 `supflag=1`，菜单仅授权页面使用的四个接口。加载及切换文件时读取业务日期，页面每 30 秒复核日期，日期变化或读取失败时清空旧结果；服务端每次请求严格核验当前日期。既有历史查询页面及模板不改动。

当前业务日期来自流程关联的 `sys_config`。查询先选择本主体最新 SUP 流程，再检查日期及成功状态，不能退回旧成功流程。成功释放节点后，根据文件导入任务结果保存的实例查询 SUP 磁盘库，不依赖已删除的节点映射。权限使用实际流程及实例的业务域和分区；实际分区为 `*` 时，全量源文件没有通用的分区裁剪列，还需覆盖全部源实例分区授权，不将样例 `01/*` 硬编码为校验条件。

### 8. 增量交付与生命周期

仅维护 `database/script/patch` 日终目录：结构和索引放 `1.table`，字典/实例/流程/加载及持久化配置放 `2.data`，流程配置保留在 `flow` 分组。本期按已确认的标准路径更新 `SHJS/SH_JSMX01` 的 `supflag`，不扩展启用 `SH_JSMX02/03` 或其他文件；后续客户个性化启用再放对应增量目录。SUP 库初始化入口沿现有实例脚本约定接入并验证可执行性。

用户确认模型已调整完成并指定手工同步 `dropruledesc`；DDL/DAO 生成之前复核字段、域类型、长度及联合主键，发现漂移只报告，不擅自改模型。用户已确认 SUP 仅有当天数据，本期不新增历史表、归档配置或历史保留策略。需核对当前数据初始化/清理的责任入口，保证旧数据及旧成功状态不混入当天结果；若需新增清理操作，仍须明确执行时点及对象范围，不能根据“无历史查询”推断任意删库权限。

## Risks / Trade-offs

- 全量数据及多实例依赖会增加内存和磁盘开销 → 文件级任务、分批缓存及流式读取，记录读取/写入/丢弃计数；具体容量阈值由部署环境决定。
- SUP 专用规则与普通流程实际导入行为不同 → 验收逐项覆盖已确认的过滤方式，不以本次结果证明普通流程的实际执行结果。
- SUP 分支当前跳过过滤，且预过滤可能提前丢行 → 覆盖创建、预过滤、正式过滤、批量写入全链路，并回归非 SUP 实例。
- 当前仅启用 `SH_JSMX01` → `SH_JSMX02/03` 共表隔离不在本期交付范围；后续扩展启用前补充批次条件和分组冲突设计，当前仍精确限定丢弃记录及文件日志。
- 配置数据采样时点与普通清算不同 → 使用本次实际加载结果分析，保留业务日期和执行上下文；基础数据就绪及业务完整性判定按用户确认不在本期范围。
- 跨库提交无法原子完成 → 以完成标志控制可见性，重试幂等恢复，流程未完成时服务端拒绝查询。
- 当前业务日期与数据/完成状态不一致 → 只开放当天查询，核验流程及文件日志的业务日期，不用前一日成功状态放行；确认当天数据准备入口。

## Migration Plan

1. 核对用户模型与本设计一致，确认当天数据准备及清理入口、客户启用清单和 SUP 实例部署参数；不部署历史归档功能。
2. 准备 Gauss 日终增量 DDL、SUP 初始化、DAO/实体及配置，保持 `supflag=0`；先审阅后按部署流程执行。
3. 部署新增功能号、运行配置、服务查询接口及页面；校验三处入口映射一致。
4. 在明确授权验证环境中用小文件完成 SUP 不支持方式报错、指定方式直接通过、席位三条件、`S/R` 兼容、忽略规则、持久化失败恢复、当天查询及非当天请求拒绝验收，再逐步启用客户清单。
5. 回退先禁用 SUP 文件开关和流程入口、停止在途任务，再回退代码及页面。新增表和结果保留供排查，不以回退为由自动删除业务数据；确认没有运行任务后释放 SUP 节点。

默认只做文档及静态核对；构建和业务测试按用户明确授权执行，不能以第三方库 CTest 替代业务验收。
