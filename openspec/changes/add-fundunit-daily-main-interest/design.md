# 新计息模式技术设计

## 当前实现与约束

需求背景及范围见 `proposal.md`，行为契约见 `specs/fundunit-daily-main-interest/spec.md`。需求编号 FS-CBS-21645，用户已确认主资金单元自身参与分算。

- 运行配置 `macbs-base/bin64/conf/frame.xml` 和模块 `export.cpp` 确认五个执行入口：`627012` 日终积数、`627013` 单客户试算、`627014` 单客户结息、`627017` 批量结息、`627020` 任务结息。
- 用户明确业务时段：`awardamt_clear`、`interest_task_settle` 用于日终；`interest_batch_settle`、`interest_single_calc`、`interest_single_settle` 用于日间。原 `Node_intradjustlog` 只有日间批量及单客户实际读取，日终任务仅有未使用的 include；本需求不扩展日终对该表的消费范围。
- `interest_base.cpp` 的 `CacheCustBusiData()` 和单客户 `CacheSingleCustBusiData()` 当前在账号结果集合与资产单元集合之间二选一。`CInterestAcctKey` 的相等及哈希只包含资金账号、币种，资产单元不能加入该键作为最终结果粒度。
- `CalcAwardamt()` 将每日计算与更新簿记绑定，直接调用它处理各子单元会将累计积数写到子单元，不能用于新模式的中间计算。
- `CalcAwardintr()` 支持日利率、年利率、未归本利息；`CalcAwardintrByFundunit()` 另有逐单元取整、尾差分配及主单元税总额逻辑，新模式不经过后者。
- 现有资金利息明细主键为 `phydate、fundacct、curcode`，不含资产单元；模式 `'1'` 当前屏蔽生成该明细。新模式虽为账号级，但同日利息、罚息积数可以并存，单个 todayawardamt 无法完整记录两者；按用户最新要求暂不记录该表，不执行 DDL。
- 三段式恢复、分段及执行模式保持不变；单客户入口沿用已有单功能号和物理库加载方式。计息执行使用 `CacheManager`，只读表优先使用已有相应 `CacheManagerPtr`；任务重做类 `CInterestTaskSettleRestore` 和积数分段类 `CAwardamtCalcRange` 按用户明确要求直接使用 `MemdbManager`。

## 设计目标与边界

**目标：** 在模块本地实现“分算输入、分类累计、主单元结果”，将一次处理内的新积数增量与历史累计状态明确分离，确保正负基数并存、日利率、未归本利息、重复试算和恢复重做时口径一致。

**边界：** 不新增功能号、表、字段、公开结果列或资产单元级利息明细；不自动迁移旧模式 `'1'` 的历史数据；不将本需求扩大为旧模式的尾差修复。新模式必需的错误分支应单独适配，避免改变旧模式计算结果。现有功能号的实际持久化边界和单客户结息状态清理规则保持原定义。

## 技术决策

### 一、新增第三个有业务含义的模式常量

在 `macbs_dict.h` 为值 `'2'` 增加含义明确的宏，建议命名 `INTR_FUNDUNIT_MODE_DAILY_MAIN`，注释为“资产单元分算当日积数，主资金单元累计计息”。保留既有两宏和默认值。

采用显式三模式判断或模块内有注释的判定方法，至少区分：

| 处理属性 | 原汇总模式 `'0'` | 原独立模式 `'1'` | 新模式 `'2'` |
|---|---|---|---|
| 当日计算输入分算 | 否 | 是 | 是 |
| 累计积数及利息保存位置 | 主单元 | 各单元 | 主单元 |
| 是否逐单元计算利息并分配尾差 | 否 | 是 | 否 |
| 结息、税及已结息状态粒度 | 账号 | 既有单元模式 | 账号 |
| 账号级利息明细 | 生成或更新 | 既有屏蔽逻辑 | 暂不生成或维护，字段不足以记录两项日积数 |

不能简单把全部 `== INTR_FUNDUNIT_MODE_INDEPENDENT` 改成“非汇总”：输入分算属于 `'1'` 和 `'2'`，结果落各单元只属于 `'1'`；扣税归属主单元属于 `'0'` 和 `'2'`，账号明细仅沿用模式 `'0'`。尤其 `DealSettleData()` 当前非 `'0'` 分支读取模式 `'1'` 专用 `m_dbTotalYSLX`，必须增加新模式主单元取税分支。

备选方案是在 `'1'` 结束后合并结果，舍弃原因是它已做利息取整、尾差分配并修改子单元簿记，无法等价实现用户要求的“先汇总积数再计算利息”。

### 二、统一按来源单元缓存，Cache完成后确定主单元

以用户更新后的日终 `awardamt_clear` 共享 `CacheCustBusiData()` 为参考：模式2直接复用 `m_mapFundunitSrcData`，各原科目Cache分支按账号、币种和来源资金单元保存余额、未交收及六类历史索引，不逐条查询或准备主单元。不使用 `m_mapSrcData` 另建账号结果，也不通过Check补全历史。

单客户 `CacheSingleCustBusiData()` 和任务 `Cache()` 使用相同科目写法；共享及任务流水分支先将结息状态和待替换流水保存到来源单元。日间调整先保留来源单元金额，实库转账始终带资金单元，按来源单元及日期保存；模式2账号级extinfo解析时明确绑定真实主单元，不生成空单元转账。各执行入口在全部缓存完成后统一调用 `CompleteMainFundunitData()`：日终积数在共享缓存之后，批量在调整缓存之后，单客户在调整及extinfo解析之后，日终任务在流水及基础资料缓存之后。单客户试算复用单客户结息Cache，不额外归集。

`CompleteMainFundunitData()` 每账号币种定位或建立真实主单元记录，设置主单元指针及标志；仅合并三类账号结息标志、待替换流水和日间调整金额。待替换流水和来源调整归集后清空，避免重复追加；转账不在该方法中合并、搬移或清空。指定单元的转账、余额、未交收及六类历史索引保持原归属，不跨单元合并；子单元历史金额不检查、不迁移、不合并、不清零。主单元无余额行仍可承载结果。

共享日终及批量缓存沿原资料加载位置，单客户保持原物理库输入和非Ptr管理器。任务基础资料随有效簿记账号加载，模式2补充仅由结息状态流水进入处理集合的账号；流水处理后从已缓存账号关联加载全部资金单元，取消整分段账号和单元扫描。客户特殊利率和客户货币利率必须由三种模式共用缓存，使用Ptr管理器及分段查询条件，按同一有效账号集合过滤，供税率和利率变更结息判断使用；任务不重新计算积数，不加载客户计息模式和计息天数。无余额主单元的结算资料及模式2周期归主仍需满足规格，目前评审发现的这两项问题单独待修复。任务专用科目、周期、三类流水状态和明细处理保持现有代码。日终不加载或消费 `Node_intradjustlog`。

五个Clear入口只从集合中的主单元记录执行模式2结果处理；每日积数遍历全部单元输入。主单元自己的余额、未交收和转账保持独立，展示合计另行汇总。删除残留但无定义的 `CacheDailyMainTransfer` 声明及调用，extinfo模式2在原解析分支直接绑定真实主单元并存入统一单元集合；仍仅允许账号级入参，未指定单元的实库转账兼容已删除。

### 三、模式2专用方法完成每日分算及主单元累计

在模块本地由 `CalcDailyMainAwardamt()` 顺序完成逐单元每日分类计算和主单元积数追加，复用 `GetTodayAwardamt()`、`GetIntrDays()` 和 `GetCumulativeMultiple()` 的业务规则。分类日结果仍保存在主单元记录的 `m_mapDailyMainAwardamt`；全部单元计算完成后，仅在 `m_bIsFirstIntr` 为真时合计分类日增量，非零增量通过原更新方法追加到主单元累计簿记，子单元簿记不修改。

定义：`B(u)` 为资产单元上一日资金余额，`A(u,d)` 为既有计息方式计算的当日基数，`M(d)` 为当日累计倍数，`X(u,d)=A(u,d)×M(d)`。

```text
新增利息积数(u,d) = X(u,d)       当 X(u,d) > 0；其余为 0
新增罚息积数(u,d) = X(u,d)       当 X(u,d) < 0 且 B(u) < 0；其余为 0

账号新增利息积数 = Σ日期 Σ全部资产单元 新增利息积数(u,d)
账号新增罚息积数 = Σ日期 Σ全部资产单元 新增罚息积数(u,d)
```

罚息保留负数符号。不能通过 `max(ΣX,0)` 或 `min(ΣX,0)` 代替上述分类累计。

日终积数、单客户试算、单客户结息及批量结息的模式2分支直接调用 `CalcDailyMainAwardamt()`，随后直接调用 `CalcDailyMainInterest()` 完成主单元应收、应付利息计算。`CalcAwardamt()` 只保留模式0/1原计算，不再嵌套模式2分支或提前返回。每个账号币种只对主单元调用一次；删除无读写用途的 `m_bDailyMainCalculated`，业务首次控制仍使用 `m_bIsFirstIntr`。日终任务结息不新增日积数计算。

### 四、仅对主单元追加增量并计算一次利息

新模式Cache已确认各单元身份；`CalcDailyMainAwardamt()` 在各输入单元计算完成后，使用同一集合中的主单元记录调用积数更新逻辑。历史累计积数只读取一次；日间调整按账号合计并仅在既有首次结息允许时追加一次，日终不从调整流水加载该合计：

```text
主单元累计利息积数 = 主单元原累计利息积数 + 当日调整合计 + 账号新增利息积数
主单元累计罚息积数 = 主单元原累计罚息积数 + 账号新增罚息积数

应收利息 = round(主单元累计利息积数 × 利息利率 / 除数 + 主单元未归本应收资金利息, 2)
应付利息 = round(主单元累计罚息积数 × 罚息利率 / 除数 + 主单元未归本应付资金利息, 2)
```

除数沿用当前实现：日利率为 `1`，年利率取对应币种利率天数 `360/365`；转账起息与积数天数另按原规则。不要混淆两种天数。

模式2入口直接调用 `CalcDailyMainInterest()`，由专用方法按主单元累计积数计算并一次取整应收、应付利息；已有记录按索引更新，零结果清掉旧非零值，缺记录仅非零时创建。`CalcAwardintr()` 删除模式2转调用分支和提前返回，仅保留模式0/1原计算；不进入模式1的取整、尾差流程。专用方法的日利率、年利率、未归本和写缓存规则均保持不变。

### 五、调整与入参转账区别处理

日间原有路径读取的调整流水先按来源单元缓存，Cache完成后由 `CompleteMainFundunitData()` 按账号、币种统一归主；无单元与指定单元调整均只追加一次，归集后清空来源调整。日终积数和任务不读取调整表，原有日间首次追加控制保持不变。

实库转账按流水 `fundunit` 和起息日归属输入单元。按用户最新要求，单客户计算和单客户结息只有模式1允许非空且非`0`的`extfundunit`；模式0/2直接报错并提示“当前模式不支持资金单元级别的单客户结息”。未传、空值或`0`均按未指定单元处理，模式1试算也不拼接单元号或筛选单元。模式2的`extinfo`转账因此始终按账号级入参归主资金单元，返回账号整体结果。

两个入口的`GetBusiParam()`先通过既有`m_objMixedCfg`读取结算主体参数`67042`，沿用物理库查询和默认模式0，再判断`extfundunit`，校验发生在Before防重短路和Cache业务加载前；不能直接判断尚未加载的默认成员值。业务值`0`使用模块本地宏`INTR_EXTFUNDUNIT_ACCOUNT`，不新增错误码配置，沿用已有异常接口及业务错误级别。本次只增加模式与入参校验，不修改模式1的转账归集、计算或结息流水范围。

既有重复单客户结息条件下，不再追加本次自然日积数和当日调整；展示所需日数据与实际追加增量分离，避免为补展示而重复更新累计状态。

### 六、五条路径共用新模式的计算与主单元结果

| 入口 | 新模式处理 | 保持的写库边界 |
|---|---|---|
| `CAwardamtClear / 627012` | 分算日积数、主单元累计、一次计算利息，不生成明细 | 缓存计算，`Write()` 批量写内存簿记，跳过明细写入 |
| `CInterestSingleCalc / 627013` | 返回账号整体积数、利息、罚息及税，依赖明细的展示字段暂保持默认值 | `Clear()` 返回 `PHASE_END`，不执行单客户结息写库 |
| `CInterestSingleSettle / 627014` | 同一计算口径，只为主单元生成单客户结息、罚息和税流水 | 原物理库簿记状态处理及预交割写库 |
| `CInterestBatchSettle / 627017` | 账号级客户筛选，通过后计算并只生成主单元预交割 | 原 `Write()` 写内存预交割主、子表，不擅自新增簿记持久化 |
| `CInterestTaskSettle / 627020` | 仅加载、使用主单元最终利息及账号级状态，按周期或利率变化结息，不加载或维护明细 | `Write()` 写正式内存主子流水，跳过明细更新 |

账号级状态需要合并同账号、币种所有相关来源流水的标志及待替换流水集合，避免沿用独立模式 `vector.at(0)` 判断整个账号。客户过滤、已有结息跳过和替换策略本身不变。

`DealSettleData()` 的新模式直接调用 `CalcTaxAmt()` 或等价主单元计算，生成一次主单元税流水；单客户覆写方法当前模式 `'0'` 扣税分支为空，新模式明确实现扣税，旧模式税行为不在本次偷偷改变。不归本结息沿用原业务类型和金额符号。

分段继续使用 `fundacct`，同账号全部资产单元必须在同一片内；恢复继续按既有主单元科目与流水范围工作，核对新模式全部写入记录是否被覆盖，仅在确有遗漏时增加最窄适配，不新增框架阶段。

### 七、模式2暂不记录资金利息明细

现有 node_fundintrdetail 只有 todayawardamt；模式0用它记录轧差后的单个日积数，而模式2可能同时产生利息积数100和罚息积数-80，无法用一个字段完整留痕。用户明确要求本阶段不扩表、暂不记录，并在关键分支保留原因注释。

GenFundIntrdetail 在模式2获取任何明细管理器前直接返回，移除此前新增的分类明细算法和更新登记；模式0方法恢复原实现。日终积数Write跳过明细插入，任务Cache/Write跳过明细加载和更新，归本、不归本及利率变更分支只在模式0维护明细。任务重做移除模式2专属明细恢复及主单元簿记读取，只保留通过MemdbManager删除任务流水。

单客户试算的返回列不变；主单元积数、利息、罚息、税和余额字段仍通过簿记填充。原依赖明细的 transferamt、transferbal、todayadjustamt、todayawardamt、intrawardamt、intrsettamt、taxsettamt、days、intrdays、ratedays 暂时保持默认值，不增加替代明细或模拟字段填充。原积数恢复的全表清理保留，本轮不新增模式2专属恢复。

### 八、配置交付仅扩展可选模式

在 Gauss 日终 `patch/gauss/fs_cbs/fs_cbs_comm/2.data/sys_param_define.sql` 追加 FS-CBS-21645 注释及参数定义增量。优先更新参数 `sysid=86、paramid=67042` 的 `dictitem、paramname、remark`，保留默认值和用户参数值；根据现有脚本及客户覆盖情况确认是否需要幂等补建定义，不能删除其他参数或替换现有需求内容。

不修改 `full`、模型 JSON、`sys_param_value` 的已选值、日间参数或客户参数启用状态；不涉及表结构、日切及归档。代码上线后由部署方按结算主体选择值 `'2'`。

## 风险与取舍

- 参数判断很多且含 `else`：逐一按输入、输出、税、明细属性核对三模式，避免新值落入旧独立模式分支或净额计算分支。
- 使用输入单元的旧簿记更新函数会污染子单元：先完成每日分类计算，再使用唯一主单元记录更新累计结果，检查所有新增、更新记录的资产单元。
- 历史利息结果只读取主单元；子单元历史记录不用于主单元历史累计，本需求不检查或自动迁移这些记录。
- 展示净余额不能还原分类积数：通过主单元累计利息、罚息积数和四类结果核对；模式2不把其中一项或净额写入旧明细字段。
- 新模式覆盖单客户和批量但写库边界不同：分别验证缓存结果、待写流水及实际写库阶段，不能把批量临时簿记计算宣称为已经持久化。
- 分算增加临时数据：集合仅保留当前分片、账号及所需日期数据，处理复杂度按输入单元数与计息日期数增长，不扩大公共框架或全局内存缓存。

## 部署与回退

1. 完成代码及 Gauss 参数定义增量交付，旧环境仍保持参数值 `'0'` 或 `'1'`。不由本提案直接执行 SQL 或切换运行配置。
2. 确认同账号全部资产单元进入同一分段、主资金单元存在；历史累计及未归本金额按主单元取值，程序不新增子单元历史存量校验。
3. 对已知数据核对新模式四类主单元结果及流水、税，并确认未生成明细，再按结算主体设置 `'2'`。
4. 回退到旧业务模式时，协调参数与代码版本；已使用新口径产生的积数不能只改参数后宣称已撤销。需要回到同一批次计算前状态并按既有恢复链路重做，或采用另行确定的跨日数据订正方案。旧二值代码运行前必须移除运行参数中的新值。

## 验证策略

按规格场景构造固定输入和预期四类结果，验证正负单元并存、主单元自身参与、历史累计加增量、日利率与未归本金额、取整差异、逐日转账、积数调整、主单元无余额、试算和不同结息入口、起扣税、恢复重做和旧模式兼容。主要比较账号级结果及实际记录归属，不只测试分支方法被调用。

实施按项目默认规则不自动执行构建或业务测试；先完成静态调用链、脚本范围、业务注释及格式检查。规格样例可作为验收数据清单；只有用户明确要求构建与测试时，再按指定 preset 或用户提供的可用环境运行对应验证，不将第三方 CTest 当作业务测试。

## 实际实现补充（2026-10-09）

新增方法集中于现有模块本地 `interest_base.h/.cpp`，未新增编译单元或改变CMake。宏采用 `INTR_FUNDUNIT_MODE_DAILY_MAIN`。模式2科目、流水、调整及转账统一按所属单元缓存，完成全部Cache后集中确定主单元并归集账号状态，不使用Check或另一账号结果集合。此前基础缓存前移及原分支直接定位主单元的设计已由本节替代。

当前源码的模式0/1/2共用原`RollFundbookkeeping()`，先通过MemdbManager翻滚内存簿记，再按原Cache科目分支缓存当日记录，不保留模式2专属翻滚列表或应用缓存翻滚分支。本轮保持用户已调整的共用翻滚实现不变。批量后续Write仍只写预交割主子流水，不另行持久化计算缓存。日终积数不读取调整流水，日间单客户及批量沿已有调整加载入口。

任务结息在模式2不加载、不更新明细，模式0处理保持原实现。任务重做在Clear写锁内通过MemdbManager按当日本任务正式主流水号删除子流水，再沿原条件删除主流水；此前新增的明细恢复、主单元及簿记读取已移除。积数恢复与批量恢复的原范围保持不变。

实施、全部模式分支引用、38组固定输入与预期结果、分段恢复检查及实际静态验证见 `implementation.md`。数值场景尚未运行业务环境验证。

日终积数分段 `CAwardamtCalcRange` 已回退为原实现，不查询调整表。共享分段基类 `CInterestBaseRange` 移除调整 Cache、include 和中转成员，仅提供默认空实现的 `CollectExtraRangeFundacct()`；日终任务不覆写该方法，分段来源保持原有簿记及转账。只有日间 `CInterestBatchSettleRange` 覆写该方法，通过 `MemdbManager` 补充当日调整账号，不按计息模式过滤，保持日间批量已有能力。日终执行仍保留转账独有账号基础资料加载；未删除日间调整独有账号的基础资料补齐。
