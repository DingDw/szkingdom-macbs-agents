## 跨实例执行与恢复

采用用户最新提出的按实例重置方式，Java 日初始化及持久化分发保持原样。C++ 前处理在独立 COMM 短事务中读取有效工作集：不存在状态则插入空集合和 0；已存在则校验分区/日期，并移除当前流程当前实例的全部计算节点。例：A 实例有 A1,A2，B 实例有 B1,B2，当前完成集合 A1,A2,B1,B2；A 前处理后只剩 B1,B2，旧状态 2 变为 1。状态 3 保留至全部节点完成。

首次并发创建不能只对不存在的状态行加锁。`ReadNodes` 在初始化时按固定顺序锁本流程已有的节点映射行，之后查询/插入状态；已存在的集合再锁状态行更新。短事务提交即释放，不等待其他实例业务工作。与其他实例成功回报交错时，由状态行锁保证成员不丢失。节点集合仍必须与全流程映射完全相等；流程配置须让参与该文件持久化的全部分配节点正常回报，不增加范围外节点的模拟成功。

失败守卫覆盖实例重置及实际数据处理，尝试独立写 3；状态写入失败保留原异常并附加日志。初始化失败且没有可用状态行时不能保证写 3；进程强杀、RPC 未进入功能号等同样不能保证状态回报，由核对超时兜底。

单节点数据重做只移除自身；实例前处理则移除本实例全部节点。重做前旧执行停止、无迟到提交/回报的约定继续适用。重复成功回报幂等。不同实例分批重做时，尚未开始前处理的实例仍可能保留上轮完成信息，导致集合暂时齐全；这是此前接受的业务重做期间核对准确性限制，本期不增加执行轮次或全局屏障。

完整批次重置与上述实例/节点局部重做不同：`clearFlowData` 在删除节点映射和流程记录前，按实际 `flowchartid` 删除本批次全部文件状态；现有当前及后置批次递归均调用该方法，下一轮前处理重新创建状态。没有记录时删除零行有效；DAO 错误直接传播。正常结束只释放节点映射时不清理状态，SUP 仍可读取业务已完成信号。此次补充仅增加专用业务 DAO/mapper 和服务注入、调用，未调整 C++ 持久化、节点调度或日切 SQL。

核对只要读到 3 就立即退出；业务修复后必须人工重新触发核对。完成集合齐全可恢复 2，但不会自动恢复已经失败的核对任务。

## 部署顺序与回退

1. 按项目发布流程，在 Gauss 的 COMM 库先执行上述新增单表 DDL，再执行归档配置和流程 9 增量配置；本次没有执行这些 SQL。配置脚本所在文件可能包含其他需求，发布时按既有版本交付流程处理，不能将整个文件当成本需求独立最小脚本。
2. 同步部署 SUP Java 与 C++ `cbs_memdb_sync`、`cbs_file`，以及相应平台入口 XML。新表要先于新版业务持久化启用，即使 SUP 仍使用模式 1。
3. 业务流程继续原调度，不要求为本变更生成协调任务。首次启用模式 2 必须先运行业务实例前处理和持久化，创建当日状态并回报节点；不能手工伪造状态 2。先前草案的协调代码与参数已移除；若曾将该中间版本部署并生成协调任务，需重新日初始化恢复原任务配置。
4. 缺省 `supmode=1`；模式 2 的 `comm_flowchartinfo.params` 示例为 `{"supmode":"2","checkpartids":"1,2,3","checktimeout":600}`；日初始化转换后的任务参数才是 `supmode=2|checkpartids=1,2,3|checktimeout=600`（具体分区使用已配置业务分区）。动态任务保存参数快照，改变参数后重新执行准备任务；不靠修改模板影响已生成任务。
5. `checktimeout` 为整个核对任务秒数，范围 1..2147483；上限来自原调度 HTTP 秒转 int 毫秒。入口静态超时上限避免原 60 秒默认值提前截断，实际任务超时使用流程参数。按阶段/批次/轮询简单检查，阻塞调用不强制取消，返回后超时即失败。
6. 日切配置为 `delete from sup_filepersistrecord`，全表清空、不归档。日切安排在原业务切日边界；不新增历史表。
7. 功能回退时设置模式 1 并重新准备 SUP 流程，删除残留核对任务、重建含 drop 的持久化配置。二进制回退按 SUP Java/C++ 版本整体交付，状态表可保留，避免在运行期间删表；业务 Java 调度保持原样，批次重置新增的状态删除需随 flowcontrol-manage-v2 和 cbs-data-flowctrol 一同部署。

客户覆盖检查：国信 patch 的流程 9 同名配置仅调整启用标志，不覆盖新增 params；其他客户 Gauss 归档同名脚本未发现整表删除/重建语句，也没有本新表配置。新增能力放标准 Gauss patch；full、OceanBase、Goldendb 和日间脚本未修改。部署顺序仍须遵循客户版本既有安装流程。

## 核对模块连接边界

`sup_file_check` 已移除全部 `Transaction` 回调和手工借还连接。配置、状态、实例发现、忽略规则复用 COMM 连接，轮询前和每轮末尾提交读事务；业务 ID 查询通过 `CXAStack` 切库并恢复。已有 `sup_filedropdata` 磁盘结果仍由 SUP 实例保存和查询，Before/Write 的 SUP 切换保留；Before 显式提交删除，Write 由 PhydbManager 的 BatchInsert 按批次提交，失败回滚当前未提交事务，已提交批次由重跑清理。本次先简化核对模块；业务持久化状态写入辅助的独立事务未调整。
