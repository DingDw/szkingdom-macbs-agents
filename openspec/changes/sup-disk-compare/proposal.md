# 未导入数据分析——磁盘库对比方案

## Why

`sup-wzrsjfx` 通过 SUP 专用过滤规则推断未导入记录，无法直接证明记录是否已进入各业务分区的磁盘库。本变更增加可选择的磁盘库对比模式：等待指定分区完成持久化后，以 SUP 全量内存记录与业务磁盘库 ID 并集的差集识别未导入数据。

## What Changes

- 新增 COMM 磁盘状态表 `sup_filepersistrecord`，按已维护模型使用 `flowchartid+intfid+fileid` 主键，记录分区、业务日期及状态 `0-未开始/1-进行中/2-完成/3-失败`。前处理匹配实际待处理表与启用接口，状态不存在时创建 `0` 和空完成集合，存在时仅移除当前实例全部计算节点成员。`finish_compute_node VARCHAR(4000)` 使用逗号分隔保存完成节点完整标识，不使用 JSON；成功回报按节点去重，只有完成集合与流程分配节点集合完全相等才能置 `2`。
- 同一文件允许跨多个业务实例；按当前流程和实例的节点映射精确移除自身成员，保留其他实例完成信息，独立短事务保护并发插入和集合更新，保持原 Java 调度。已有失败状态不被前处理清除。
- 支持单节点独立重试和重做；用户已保证重做前旧执行完全停止且不会再提交或上报。重新持久化前仅移除该节点旧完成标识，其他节点完成信息保留。失败后继续维护完成集合，全部节点完成才恢复状态 2；核对任务检测到状态 3 立即报错退出，随后只能由人工重新触发，不自动重试或恢复。
- 批次重置时按实际 `flowchartid` 同步删除 `sup_filepersistrecord`，沿用现有当前及后置批次递归清理入口，防止重新分配计算节点后残留上批状态。正常流程结束释放计算节点时保留状态，供后续 SUP 核对使用。
- 日切通过归档配置的 `deletestr` 全表清空 COMM 状态表，采用只删除、不归档方式，使旧业务日的完成标志不能用于新一天核对。用户称配置表为 `comm_archivecfg`；当前模型和 Gauss 脚本中的实际表名为 `comm_archive_cfg`。
- 流程启动查询的 `base_column_list` 补齐 `params`；真实初始化入口 `DayInitHandler.dayInit()` 在入参参数为空时按模板编号兜底读取，并从最终实例参数合并任务参数。合并后再建流程缓存，保证实例、任务和缓存参数一致，避免 SUP 模式配置丢失；已生成实例需重置后重新初始化。
- 流程 `9` 增加 `supmode`、`checkpartids`、`checktimeout`；缺省模式为 `1`，保持原方案。模式 `2` 按指定分区等待，整个核对任务总超时默认 `600` 秒，采用简单的经过时间检查，不要求精确中断每次阻塞调用。
- 模式 `2` 的 SUP 导入跳过数据过滤及忽略规则检查，也不清理或生成丢弃记录；源数据持久化不再生成 `sup_filedropdata` 配置。保留解析、字段转换及记录 ID 的完整性校验。
- 模式 `2` 为每个文件生成依赖本文件持久化的核对任务。先清理本文件旧结果，再按已确认的同一业务日、分区、接口、文件唯一业务流程约定，等待全部指定分区状态为 `2`；无记录或状态 `0/1` 继续等待，状态 `3` 立即失败，超时明确退出。
- 从已通过等待的分区查找全部实例，并补充这些实例所属业务域的 `insttype='2'` NODEX 实例，去重后仅读取当前文件源表的 `id`。SUP 内存中存在、全部业务磁盘库均不存在的记录生成丢弃结果，并复用原忽略规则表达式与文件范围；模式 `2` 按用户确认采用 MemDB 字段值比较。用户已确认 `dropruleid` 留空，`dropruledesc` 固定为“指定分区磁盘库中未找到记录”。
- 按当前接口文件的 `comm_if_file.zkflag` 限制磁盘查询范围：值为 `2`（只导入 NODEX）时不查询普通节点库（`insttype='1'`）的源表，仅查询 NODEX（`insttype='2'`）；仍按指定分区等待持久化状态，其他标志保留原实例选择逻辑。没有可查询 NODEX 时明确报错。
- 模式 `2` 核对任务仅维护 SUP 磁盘库结果，不清理或写入 MemDB 丢弃结果；流程清理及查询完成判定覆盖核对任务，失败或未完成时不发布成功分析结果。

## Capabilities

### New Capabilities

- `sup-business-file-persist-state`：业务文件持久化状态、可见性、重做和日切清理。
- `sup-disk-compare-mode`：模式参数、动态文件核对任务、模式分流及结果查询兼容。
- `sup-disk-file-reconciliation`：等待状态、业务磁盘实例发现、ID 差集、忽略标志和结果落库。

### Modified Capabilities

无已归档主规范需要修改。已检查 `openspec/specs`：原 SUP 三项能力仍位于未归档变更 `sup-wzrsjfx`。本变更引用其模式 `1` 行为，新增模式 `2` 的覆盖规则，不复制原能力为另一套主规范；归档时先同步原方案，再同步本增量。

## Impact

- `macbs-base`：`cbs_memdb_sync` 的 `600003/600001` 状态维护；`cbs_file/file` 的 SUP 模式分流及新增单功能号核对入口；业务层共享状态辅助、业务宏、入口注册及构建清单（不在自动生成 DAO 中维护手工逻辑）。
- 持久化代码遵循最小改动约束：新增接口匹配、状态维护和节点集合处理尽量提取为独立函数，原有主流程只增加必要调用，保持执行结构清晰，不因本次改造扩展无关重构。
- `macbs-service`：`modules/supfile` 的准备、持久化配置、清理及查询完成判定；`flowcontrol-manage-v2` 的批次重置及 `cbs-data-flowctrol` 的专用状态清理 DAO；日终 Gauss `script/patch` 的新增表、流程参数与日切配置。原状态字段 `comm_if_file_log.persiststatus` 的二值语义保持。
- 新增核对采用单一功能号、清算七阶段；按用户明确授权，源表直接通过 MemdbManager 获取表句柄并逐条读取内存库记录指针，丢弃结果通过 PhydbManager 暂存，并在 Write 调用 `BatchInsert()` 写入 SUP 磁盘；状态和忽略配置直接访问 COMM 磁盘库。
- 本期延续原启用范围 `SHJS/SH_JSMX01`，代码仍由配置驱动，不自动扩展文件开关；共表多文件隔离需另行确认后扩展。
- 用户已接受核对期间业务磁盘表可能被重做或修改的风险：本期不解决该并发场景，不增加跨库快照、业务写入锁、二次状态复核或自动重试，不将停止业务写入作为运行前置条件；此场景下结果可能不准确。
- 本变更已进入实施，修改业务代码及增量 SQL，不修改用户维护的模型 JSON；按仓库约定未运行构建或数据库脚本。用户已确认模型 JSON 已维护，现已复核新表七个字段和联合主键。本次增量沿用需求编号 `FS-CBS-7768`，SQL 注释及交付标识统一使用该编号。
