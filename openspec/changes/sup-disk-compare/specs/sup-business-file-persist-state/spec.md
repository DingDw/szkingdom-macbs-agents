## Purpose

为日终公募、私募、普通等业务分区的文件数据提供统一、可观察的磁盘持久化状态，使 SUP 文件核对能够等待完整数据提交，识别失败与超时，并通过日切清理避免将前一业务日的完成信号用于新一天分析。

## ADDED Requirements

### Requirement: 业务文件状态存储于 COMM 磁盘库
系统 MUST 在 COMM 库维护 `sup_filepersistrecord`，采用 `flowchartid+intfid+fileid` 联合主键，保存 `partid`、`busidate`、`finish_compute_node VARCHAR(4000)` 和 `persiststatus`，按当前业务日的 `partid+intfid+fileid` 查询相关流程状态。完成节点 MUST 使用逗号分隔的完整节点标识，不使用 JSON。`persiststatus` MUST 使用 `0-未开始`、`1-进行中`、`2-完成`、`3-失败`，不得与 SUP 文件日志的二值持久化标志混用。SUP 自身源数据持久化不得覆盖或冒充被检查业务分区的完成状态。

#### Scenario: 业务分区与 SUP 分别持久化同一文件
- **WHEN** 业务分区和 SUP 实例均持久化同一接口、文件的源表
- **THEN** COMM 中业务分区状态仅反映该分区业务持久化，SUP 自身完成不能使该业务分区被判定为完成

### Requirement: 前处理按实际工作集创建状态或清空当前实例节点
系统 MUST 将本次有效持久化表集合与 `comm_if_file` 中 `supflag='1'` 的接口目标表精确匹配。按 `flowchartid+intfid+fileid` 查询状态：不存在时 MUST 插入实际分区、业务日期、空完成集合及状态 `0`；存在时 MUST 只移除 `comm_inst_compute_node_map` 中当前 `flowchartid+instid` 所分配的计算节点，保留其他实例成员，不删除重建整条记录。操作 MUST 在目标表前处理之前以独立 COMM 事务提交；日期或分区不符 MUST 报错。未命中的文件及其他流程保持不变。

已有 `3` MUST 保留，直到全部节点完成才恢复 `2`；已有 `1/2` 在实例前处理后为 `1`；已有 `0` 且仍为空集合可以保持 `0`。前处理不得发布 `2`。同一实例重复前处理会再次清除自身节点，应在本实例旧执行停止后进行，不与单节点数据重做混淆。

#### Scenario: 状态尚未建立
- **WHEN** 当前流程文件没有状态记录
- **THEN** 创建唯一的当天记录，状态 `0`、完成集合为空

#### Scenario: 当前实例重做而另一实例已完成
- **WHEN** 状态为 `2`，集合为 `A1,A2,B1,B2`，当前实例分配节点为 `A1,A2`
- **THEN** 保留 `B1,B2`，状态改为 `1`，不清空其他实例信息

#### Scenario: 失败后再次前处理
- **WHEN** 状态为 `3`，当前实例重新前处理
- **THEN** 仅移除当前实例成员并保留状态 `3`，不掩盖其他节点失败

#### Scenario: 配置相似表或非本次范围
- **WHEN** 工作集只有 `sh_jsmx_bak`，接口目标为 `sh_jsmx`，或接口未启用
- **THEN** 不创建或修改该接口状态

#### Scenario: 多条配置命中同一文件
- **WHEN** 本次有效配置多次命中同一接口文件
- **THEN** 同一状态只处理一次，不产生重复逻辑记录

#### Scenario: 初始化或实例重置事务失败
- **WHEN** 状态插入、更新或提交失败
- **THEN** 回滚本次状态事务，当前前处理报错退出，不继续修改目标表；尝试独立回报失败，回报错误不得掩盖原异常

### Requirement: 跨实例前处理并发保护且保持原调度
系统 MUST 保持原实例前处理和持久化调度，不新增 Java 流程级协调任务。首次创建状态与已有集合修改 MUST 有并发保护：初始化事务按固定顺序锁定当前流程稳定的计算节点映射行，解决状态行不存在时的并发插入；已有状态行读改写再加行锁，避免覆盖其他节点刚提交的完成信息。锁 MUST 在状态事务结束时释放，不持锁等待其他实例前处理或数据持久化。流程及当前实例的节点映射为空 MUST 报错。

#### Scenario: 两实例同时首次前处理
- **WHEN** A、B 同时发现当前文件需要初始化
- **THEN** 初始化串行判定存在性，只创建一条记录，不发生主键冲突；后进入者仅移除自己实例成员

#### Scenario: B 前处理晚于 A 节点成功
- **WHEN** A1 已回报完成，而 B 随后执行前处理
- **THEN** B 只移除 B 实例节点，保留 A1；不要求 A 等待 B 前处理

#### Scenario: 前处理和另一实例成功回报并发
- **WHEN** B 正在修改集合，A1 同时回报成功
- **THEN** 状态行锁保护读改写，最终保留 A1，不发生字符串覆盖丢失

#### Scenario: 同一天多实例先后重做的已接受限制
- **WHEN** 上轮全部完成，A 本轮重做已完成而 B 尚未开始本轮前处理
- **THEN** B 上轮完成成员仍可能保留；本期不以执行轮次隔离或统一屏障识别该时间窗，沿用业务重做期间核对结果可能不准确的已接受限制

### Requirement: 持久化状态反映已提交的完整工作
系统 MUST 在对应文件正常首次持久化开始时提交状态 `1`，仅在该文件当前分区所有相关数据任务成功且数据已提交后发布 `2`。任何相关持久化错误 MUST 移除本节点完成标识、发布 `3` 并使任务失败，后续其他节点的局部成功不得覆盖尚未恢复的失败。多批次、多任务场景不得以单个批次完成代表分区完成；零行数据完成实际清理和持久化处理后同样允许发布 `2`。

#### Scenario: 仍有工作未完成
- **WHEN** 一个批次已成功，但对应文件仍有相关数据任务未完成或事务未提交
- **THEN** 文件分区状态不为 `2`，核对不能开始

#### Scenario: 全部相关数据已提交
- **WHEN** 当前分区该文件全部相关持久化成功提交，且没有本轮失败
- **THEN** 状态更新为 `2`，其他连接可读取该完成状态和已提交数据

#### Scenario: 持久化报错
- **WHEN** 读取、更新、merge、插入或提交过程中任一相关任务报错
- **THEN** 本轮任务失败并将对应状态持久化为 `3`；失败数据事务回滚不得同时回滚该失败信号

#### Scenario: COMM 状态库不可用
- **WHEN** 数据持久化报错且失败状态也无法写入 COMM
- **THEN** 返回失败并记录两类错误，不宣称状态 `3` 已保存，也不发布状态 `2`

#### Scenario: 空表完成
- **WHEN** 文件目标表本轮没有待写数据，但本轮所需删除和持久化工作全部成功
- **THEN** 正常发布状态 `2`，不因零行数据永久停留在等待状态

#### Scenario: 实际持久化缺少前处理记录
- **WHEN** 实际持久化开始更新状态时找不到应有的初始化记录
- **THEN** 报告状态链路异常，不能静默生成完成标志

### Requirement: 按流程分配节点集合汇总完成状态
系统 MUST 以 `comm_inst_compute_node_map` 中分配给当前 `flowchartid` 的全部计算节点完整标识构成目标集合。每个节点成功完成当前文件的全部本地持久化后，MUST 在并发保护的事务内将自己加入 `finish_compute_node` 集合并去重。完成集合与目标集合完全相等才满足状态 `2` 的完成条件，不能仅比较数量。正常无失败时，未齐全保持 `1`。集合更新与状态判定 MUST 同事务提交；节点映射不得在本轮中途改变。发生失败后，业务节点重试 MUST 继续维护完成集合，未齐全时保持状态 3，集合齐全且相关数据已提交后才恢复状态 2；不得仅因某节点开始重试或局部成功而清除失败。

#### Scenario: 三个节点逐步完成
- **WHEN** 当前流程分配三个计算节点，节点依次成功完成同一文件
- **THEN** 完成集合依次包含一个、两个、三个不同节点，正常无失败时状态依次为 `1/1/2`

#### Scenario: 两个节点并发成功
- **WHEN** 当前完成集合为空，两个计算节点同时回报成功
- **THEN** 最终集合保留两个节点，不因字符串覆盖丢失任一节点，并按目标集合判定状态

#### Scenario: 节点有多个内部批次
- **WHEN** 同一节点以多个线程、多个批次或多条相关配置持久化同一文件
- **THEN** 仅在该节点相关工作全部成功后加入集合，重复回报同一节点不产生重复元素

#### Scenario: 某节点失败后其余节点成功
- **WHEN** 某失败节点尚未恢复，其他节点随后启动或完成
- **THEN** 不能仅因其他节点的局部进展清除状态 `3` 或发布成功

#### Scenario: 重复成功回报
- **WHEN** 节点成功状态提交后响应丢失，重试同一次执行的成功回报
- **THEN** 按完整节点标识去重，不重复追加，不让其他未完成节点被误判为已完成

#### Scenario: 数量相同但节点不同
- **WHEN** 目标集合为 A、B，完成集合却包含 A、C，或某回报节点不属于目标集合
- **THEN** 报告节点归属异常，不因数量相等而发布成功

### Requirement: 逗号节点列表精确解析且不截断
系统 MUST 使用逗号分隔的完整节点标识，按元素精确匹配、去重，不用子串匹配。空字段表示空集合，规范写入不得含空元素或首尾逗号。节点标识为空、含逗号或序列化结果超过字段 4000 长度限制 MUST 报错，不得截断后继续成功。

#### Scenario: 地址前缀相同
- **WHEN** 两个节点地址具有包含关系但完整值不同
- **THEN** 将其识别为不同节点，不因子串命中误判另一节点完成

#### Scenario: 列表超过容量
- **WHEN** 加入节点后的规范列表超过字段容量
- **THEN** 本次状态更新失败并明确报错，不保存截断的完成列表

### Requirement: 单节点重做只失效自己的完成标识
系统 MUST 支持单节点独立重做，前提是用户已确认旧执行完全停止、不会再提交数据或上报状态。真正重新执行持久化前 MUST 移除本节点原完成标识并使原完成状态失效，成功后再加入；其他节点完成信息 MUST 保留，不要求全部节点清空后重跑。仅重试同次执行的成功状态回报不属于重新执行数据持久化，不移除有效完成信息。

#### Scenario: 已成功节点独立重做
- **WHEN** A、B 均已成功，确认 A 的旧执行已停止后单独重做 A
- **THEN** 在 A 修改数据前将完成集合变为仅 B 并使原成功状态失效；A 再次成功后恢复 A、B 集合，B 不必重做

#### Scenario: 实例前处理与单节点重做范围不同
- **WHEN** 用户重做实例前处理或只重做其中一个节点的数据持久化
- **THEN** 前者移除本实例全部分配节点，后者只移除自身；都保留其他实例成员

### Requirement: 批次重置按实际流程编号同步删除状态
系统 MUST 在清理业务批次流程数据时，以该批次实际 `flowchartid` 删除 `sup_filepersistrecord` 中该流程全部文件记录，覆盖当前批次及现有递归清理涉及的已实例化后置批次，不使用模板编号或重新分配后的节点列表作为删除条件。状态删除 MUST 先于节点映射和流程记录删除；清理失败 MUST 传播，不能忽略错误继续正常初始化。其他批次的状态 MUST 保留；删除零行可以正常完成。完整清理后，新一轮前处理 MUST 创建空完成集合及初始状态，不能继承上批完成节点。

#### Scenario: 当前和后置批次重新初始化
- **WHEN** 清理当前业务批次及其已实例化后置批次，并准备重新分配计算节点
- **THEN** 按各批次实际流程编号删除对应文件状态；新节点不读取上批完成集合，其他流程状态保持不变

#### Scenario: 模板编号与实际流程编号不同
- **WHEN** 清理某个由模板生成的实际业务批次
- **THEN** 删除实际 `flowchartid` 的状态，不误删模板或其他实例化批次的记录

#### Scenario: 批次没有文件状态或重复清理
- **WHEN** 批次状态记录不存在，或再次执行相同批次清理
- **THEN** 删除零行正常完成，不报缺失错误，也不扩大清理范围

#### Scenario: 状态删除失败
- **WHEN** 删除当前或后置批次状态时发生数据库错误
- **THEN** 清理调用报错，不将该批次正常清理后重新初始化；可重试清理，不发布清理成功

### Requirement: 正常结束释放计算节点保留状态
正常业务流程结束释放计算节点映射时 MUST 保留 `sup_filepersistrecord`，供随后执行的 SUP 核对读取；通用节点释放入口不得附加状态删除。保留的状态仍受批次重置和日切清理约束。

#### Scenario: 业务已完成并释放计算节点
- **WHEN** 业务文件持久化状态为 `2`，业务流程正常结束并释放节点映射
- **THEN** 文件状态仍为 `2`，SUP 核对可以据此继续实例发现和磁盘查询

### Requirement: 日切通过删除配置清空状态
系统 MUST 在 COMM 日切删除流程通过 `comm_archive_cfg.deletestr` 清空 `sup_filepersistrecord` 全表记录，采用只删除、不归档方式，不建立历史表或归档文件。删除 MUST 完成于次日业务持久化启动之前；用户所称 `comm_archivecfg` 对应当前模型中的 `comm_archive_cfg`。

#### Scenario: 日切存在各类状态
- **WHEN** 状态表中同时存在不同分区的 `0/1/2/3` 记录并执行日切
- **THEN** 全部记录清空，不按分区、日期或状态保留任一行；次日查询缺失记录按未完成处理

#### Scenario: 日切删除失败
- **WHEN** 状态清理 SQL 执行失败
- **THEN** 日切任务报错，不宣称清理完成，不允许将旧状态当作次日就绪依据
