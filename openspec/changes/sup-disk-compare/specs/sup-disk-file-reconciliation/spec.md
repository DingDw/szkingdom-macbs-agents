## Purpose

对已全量导入 SUP 的文件，等待所选业务分区完成持久化，发现全部应查询的业务磁盘实例并计算原始 ID 差集，生成保留源记录身份与忽略标志的未导入结果，严格区分缺失事实、配置错误和查询执行失败。

## ADDED Requirements

### Requirement: 核对首先清理当前文件旧结果
每次模式 `2` 文件核对 MUST 在开始等待分区状态之前，实际删除 SUP 磁盘 `sup_filedropdata` 中当前 `intfid+fileid+busidate` 的旧结果，其他文件、接口和日期保持不变。模式 `2` 不清理或写入 MemDB 丢弃结果；模式 `1` 保持原处理。清理失败 MUST 终止任务。后续结果为空也不得残留旧数据；任务失败时不得将空表或局部结果解释为成功。

#### Scenario: 重做后没有缺失记录
- **WHEN** 上次该文件存在丢弃结果，本次磁盘已包含全部源 ID
- **THEN** 当前文件旧结果被清空，成功后结果为空，其他文件结果保持不变

#### Scenario: 清理后轮询失败
- **WHEN** 清理成功但后续状态等待失败或超时
- **THEN** 当前任务失败，查询不可将刚清空的结果当作完整成功结论

### Requirement: 所有指定分区成功才允许读取业务磁盘
核对 MUST 按 `checkpartids` 中所有不同分区及当前 `intfid+fileid+busidate` 轮询 COMM 状态，并保留每条状态的 `flowchartid` 维度。用户已确认同一业务日、partid、intfid、fileid 只对应一个待检查业务 flowchartid。系统 MUST 对每个分区的唯一匹配记录判断状态，记录为 2 才算完成；出现多条匹配记录 MUST 报错，不任意选择一条。无记录、`persiststatus='0'/'1'` MUST 继续等待；任一状态 `3` MUST 立即报错退出，不继续轮询等待恢复，不自动重试或自动重新调度；退出后必须由人工重新触发核对，业务状态自行恢复为 2 不改变已失败的核对任务结果。全部指定分区完成才允许开始业务磁盘 ID 查询。未知或 NULL 状态 MUST 报错。轮询 MUST 能看到其他事务新提交状态并以 `checktimeout` 作为整个核对任务总超时，采用简单经过时间检查。

#### Scenario: 三个分区不同进度
- **WHEN** 分区 1 为 `2`、分区 2 为 `1`、分区 3 尚无记录
- **THEN** 继续轮询三个分区，不开始 ID 差集计算

#### Scenario: 任一分区失败
- **WHEN** 分区 2 为 `3`，其他分区仍等待或已成功
- **THEN** 立即报错退出并指出分区 2、接口和文件，不等待其他分区直至超时

#### Scenario: 所有分区完成
- **WHEN** 指定的全部分区状态均为 `2`
- **THEN** 开始实例发现及业务磁盘查询，不额外等待未指定分区

#### Scenario: 长时间缺记录或未完成
- **WHEN** 轮询检查发现本次任务总经过时间达到 checktimeout，仍存在无记录或状态 `0/1` 的分区
- **THEN** 核对超时失败，报告未完成分区及最后状态，不将缺记录当作“该分区不需要核对”

#### Scenario: 同一分区违反唯一业务流程约定
- **WHEN** 当前业务日相同 partid、intfid、fileid 查到多个 flowchartid 的状态记录
- **THEN** 报告记录歧义并退出，不因其中一条或全部记录为 2 而通过核对

#### Scenario: 只有旧业务日完成记录
- **WHEN** 当前分区只存在同一文件旧业务日的状态 `2`
- **THEN** 当前业务日按无记录继续等待，不能复用旧日期状态

#### Scenario: 业务恢复后核对由人工重新触发
- **WHEN** 核对因状态 3 已失败退出，随后业务节点重试使全部相关状态恢复为 2
- **THEN** 原核对任务仍保持失败且不自动执行，由人工重新触发后执行完整清理、等待和核对流程

#### Scenario: 人工重新触发时失败尚未恢复
- **WHEN** 人工重新触发核对，但任一被检查状态仍为 3
- **THEN** 核对再次立即报错退出，不因属于人工重试而忽略失败或延长等待

### Requirement: 实例集合包含指定分区全部业务实例与对应域 NODEX
核对 MUST 按已通过等待的分区查询 `comm_instance` 中全部当前业务实例，再根据这些实例的 `domainid` 补充所有 `insttype='2'` 的 NODEX，按 `instid` 去重后查询。SUP 自身和历史库不得作为业务导入证据。分区业务实例缺失、应有域级 NODEX 缺失或连接配置无效 MUST 报错，不能用不完整集合生成结论。

当前文件 `comm_if_file.zkflag='2'`（只导入 NODEX）时，磁盘 ID 查询集合 MUST 排除全部 `insttype='1'` 普通业务实例，仅包含 `insttype='2'` NODEX；可以查询普通实例的 COMM 元数据以校验分区和确定业务范围，但不得连接普通节点查询源表。其他标志保持原有实例选择逻辑。仅 NODEX 模式没有任何可查询 NODEX 时 MUST 报错，不能生成全部缺失的成功结论。指定分区的持久化状态等待规则 MUST 保持。

#### Scenario: 只导入 NODEX 且普通节点没有源表
- **WHEN** 当前 `intfid+fileid` 的 `zkflag='2'`，指定分区已完成持久化，普通节点没有源表而 NODEX 已保存该表
- **THEN** 不查询普通节点源表，只读取 NODEX 的 ID 并计算差集，不因普通节点缺表失败

#### Scenario: 只导入 NODEX 但目标实例缺失
- **WHEN** 当前文件 `zkflag='2'`，没有任何可查询 NODEX 实例
- **THEN** 核对明确报错，不将空实例集合视为成功的空磁盘数据

#### Scenario: 只导入 NODEX 仍等待业务持久化
- **WHEN** 当前文件 `zkflag='2'`，指定分区状态无记录、为0/1或为3
- **THEN** 分别继续等待或立即失败，不因不查询普通节点表而跳过状态检查

#### Scenario: 其他文件保持原查询范围
- **WHEN** 当前文件 `zkflag` 不是 `2`
- **THEN** 按原逻辑选择普通节点及 NODEX，目标节点源表不存在或查询失败仍正常报错

#### Scenario: 一个分区有多个业务实例
- **WHEN** 指定分区包含两个实例，缺失候选 ID 只存在于第二个实例
- **THEN** 查询覆盖两个实例，该 ID 不被判定为未导入

#### Scenario: 跨域分区和共享 NODEX
- **WHEN** 指定分区分别属于不同业务域，多个分区又共享同一 NODEX
- **THEN** 补齐各域对应 NODEX，共享实例只查询一次，不把范围错误限制为 SUP 自身业务域

#### Scenario: 只有 SUP 磁盘包含记录
- **WHEN** 某 ID 在 SUP 磁盘中存在，但所有应检查的业务磁盘都不存在
- **THEN** 该 ID 仍属于未导入，不因全量导入自身的持久化而通过核对

### Requirement: 使用全部业务磁盘 ID 并集计算差集
核对 MUST 根据任务 `intfid+fileid` 获取合法目标表，对每个已发现的业务磁盘实例只查询 `id` 列到内存，去重后与仍保留在 SUP MemDB 的当前文件记录比较。源记录 ID 不在任何业务磁盘 ID 集合中时才生成未导入记录；存在于任一实例即不属于未导入。ID MUST 保留原整数精度，不重新编号或截断 BIGINT。任何目标库查询失败、表缺失或字段错误 MUST 使核对失败，不能当作空结果。

业务前提已经用户确认：SUP 与各业务流程针对同一 fileid 的物理文件清单及文件序号映射一致，使用既有 ID 直接关联源记录。

范围限制已经用户确认：本期不解决核对读取期间业务磁盘表被并发重做或修改的情况。差集依据各次实际读取的 ID 集合生成，不承诺跨库同一时点一致性或该并发场景下结论准确；不要求写入隔离、额外快照、二次状态检查、自动重试或先停止核对。

#### Scenario: 相同文件记录跨流程比较
- **WHEN** SUP 和业务流程按已确认一致的物理文件清单与文件序号映射导入同一文件记录
- **THEN** 使用原有记录 ID 比较存在性，不对 SUP 记录另行编号或引入新的文件身份键

#### Scenario: 并集而非各库交集
- **WHEN** SUP 源 ID 为 `{1,2,3}`，业务库 A 含 `{1}`，业务库 B 含 `{2}`
- **THEN** 只生成 ID `3` 的未导入记录，ID `1/2` 不要求在所有库同时存在

#### Scenario: NODEX 命中
- **WHEN** 某源 ID 在所有分区节点库中缺失，但在对应域 NODEX 存在
- **THEN** 不生成该 ID 的未导入记录

#### Scenario: 重复与大整数 ID
- **WHEN** 同一 BIGINT ID 出现在多个业务库且超过浮点精确整数范围
- **THEN** 仍按原整数值精确判断存在，不重复计数或误判缺失

#### Scenario: 有效空库
- **WHEN** 所有目标实例查询成功，某个或全部目标表返回零行
- **THEN** 将成功的零行结果视为空 ID 集合，按完整并集计算差集

#### Scenario: 一个库查询失败
- **WHEN** 多个目标库中有一个连接失败、表不存在或查询报错
- **THEN** 整个核对失败，不以其余成功查询的集合发布缺失结果

### Requirement: 差集记录使用统一原因并保留记录身份
系统 MUST 按 `intfid+fileid+id+busidate` 保存每条未导入记录，`id` 直接来自 SUP 原始源记录。模式 `2` 的 `dropruleid` MUST 留空，`dropruledesc` MUST 为“指定分区磁盘库中未找到记录”；不得重新执行过滤规则生成推测原因或伪造过滤规则编号。

#### Scenario: 文件配置含多个过滤规则
- **WHEN** 某条源记录确实不在任何业务磁盘中，但文件存在若干可能拒绝它的过滤规则
- **THEN** 仍保存空规则编号和统一磁盘缺失原因，不以规则推演替代差集事实

### Requirement: 仅对差集记录按原语义标记忽略
核对 MUST 复用原方案忽略规则的文件范围、字段映射、表达式及任一命中语义，从 COMM 读取当前 `intfid+fileid` 规则。模式 `2` MUST 按 MemDB 类型化字段值求值，整数不转浮点，字符串延续原首尾空白处理后精确比较；无需恢复导入前数值文本。模式 `1` 保持原解析文本语义。任意规则命中则 `dropignoreflag='1'`，否则 `'0'`；规则错误或无法取得所引用字段 MUST 使核对失败。忽略标志不得删除缺失记录或改变未导入事实，查询不得临时重新计算标志。

#### Scenario: 命中忽略规则
- **WHEN** 一条差集记录命中当前接口、文件的任一忽略规则
- **THEN** 保留该未导入记录和统一原因，忽略标志置为 `1`

#### Scenario: 无规则或其他文件的规则
- **WHEN** 当前文件没有规则或均未命中，仅其他文件配置可匹配当前字段
- **THEN** 当前缺失记录的忽略标志为 `0`

#### Scenario: 忽略规则字段映射不完整
- **WHEN** 规则引用字段无法通过文件元数据映射到本次 MemDB 源表字段
- **THEN** 核对明确失败，不用空值或其他字段悄然代替

#### Scenario: 数值文本已被转换
- **WHEN** 文件数值文本为 `001`，MemDB 对应整数值为 `1`
- **THEN** 模式 `2` 按整数值比较，规则数值 `1` 与 `001` 都匹配，不保存或重建原始文本

#### Scenario: 修改规则后重做核对
- **WHEN** 修改或删除忽略规则后重新执行同一文件核对
- **THEN** 清理旧结果并依据新规则生成标志；只查询旧成功结果时保持原已保存标志

### Requirement: 核对结果写入 SUP 磁盘后才发布成功
模式 `2` 核对 MUST 仅将生成结果写入 SUP 磁盘的 `sup_filedropdata`，通过 `CSup_filedropdataPhydbManager` 暂存并在 Write 调用 `BatchInsert()` 批量插入，不维护 MemDB 丢弃结果，不依赖已完成的源表持久化任务再次处理结果表。只有本轮完整结果成功写入后才发布核对成功；任何磁盘批次失败均使任务失败，已提交批次不得被发布为完整结果，重做先清理再生成，不残留旧结果、重复结果或成功标志。

#### Scenario: 磁盘批次写入失败
- **WHEN** 磁盘结果任一批次写入失败
- **THEN** 核对任务失败且查询结果不可用；重跑按本文件范围清理后重新计算

#### Scenario: 结果为零条
- **WHEN** 当前源记录为空或全部 ID 已在业务磁盘中存在，其他检查全部通过
- **THEN** 完成旧结果清理并发布有效空结果，查询可明确显示无未导入记录
